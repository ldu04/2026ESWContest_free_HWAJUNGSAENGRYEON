# LED 상태 표시 현황과, ETA 경보 하향 경로의 비용 (2026-08-31)

## 1. 현재 상태 머신 — WARN 상태는 **없다**

`firmware/node/node.ino:45`

    enum NodeState { ALIVE, DYING, DEAD };

세 갈래뿐이다. LED 도 두 색이다 (`node.ino:155-159`):

    if (state == ALIVE) 초록(0,90,0)
    else                빨강(120,0,0)      // DYING·DEAD 공용

`WARN_TEMP_C` 는 이미 있지만 **자기 상태에는 쓰이지 않는다.** 쓰이는 곳은 한 군데다:

    node.ino:392   bool hot = (n.peakTemp >= WARN_TEMP_C) || (curTemp >= WARN_TEMP_C);

이건 **이웃의 사망을 투표할 때 쓰는 '고온 정황' 판정**이지, 자기 상태 전이가 아니다.
전이는 `TEMP_THRESHOLD_C` 하나로만 일어난다(`ALIVE → DYING`, `node.ino:356`).

**지시대로 WARN 상태를 추가하지 않았다.** 추가하려면 enum·전이·LED·배너·문서가 같이 움직여야 하고,
그건 촬영 전날에 할 일이 아니다.

## 2. ★ 서사에서 섞이면 안 되는 두 가지

| | 뜻 | 지금 있는가 |
|---|---|---|
| **(가) 자기 온도 경고** | 그 노드 자신의 온도가 WARN 을 넘었다 | **없다** (상태로 존재하지 않음) |
| **(나) ETA 경보** | 이웃들의 **죽음**으로부터 계산한 도착예상시각이 임박했다 | **있다 — 게이트웨이·대시보드에만** |

**(가)를 켜놓고 (나)라고 말하면 거짓이 된다.**
(가)는 온도계 한 개의 자기 보고이고, (나)는 여러 노드의 죽음을 모아 만든 추정이다.
이 프로젝트의 주장은 (나)에 있다.

### 덱·문서에서 섞여 있는 곳 — 확인 결과

| 위치 | 문구 | 판정 |
|---|---|---|
| **덱 v9 발표4** | 「상태 표시: WS2812 LED (**생사·경보** 시각화)」 | **★ 사실과 다르다.** LED 는 **생사만** 표시한다. 경보는 대시보드에만 있다 |
| 덱 v9 발표5 | 「**대시보드**가 … 대피경보를 실시간 재생」 | 정확 — 주체가 대시보드로 명시돼 있다 |
| 덱 v9 발표18 | 「'이 구역에 화선 N분 내 도달' 대피 타이밍 제공」 | 정확 — 화면 기능 설명이고 LED 를 말하지 않는다 |
| `docs/cowork/하드웨어_H0_브링업_가이드_및_펌웨어스펙.md:51` | 「LED 상태(온도 밴드): COOL 초록 / WARM 50~60℃ 호박 / HOT ≥60℃ 빨강」 | **구현되지 않은 옛 스펙.** 실제는 2색 |
| `docs/구현지시서_4_펌웨어포팅.md:37` | 「LED: ALIVE=초록 / DYING·DEAD=빨강」 | 정확 — 현행과 일치 |

**덱 v9 는 동결이라 고치지 않았다.** 발표4 의 「생사·경보 시각화」 한 곳이 걸린다.
영상 내레이션·발표 멘트에서는 **「LED 는 생사, 경보는 화면」** 으로 말해야 한다.

## 3. ETA 경보를 노드로 내려보내는 경로 — **지금 없다.** 비용만 적는다

### 현재 데이터 흐름은 단방향이다

    노드 --(메시)--> 브리지 --(USB 시리얼)--> 게이트웨이 --> 대시보드
                                     ↑ 읽기 전용

`gateway/serial_source.py` 는 `readline()` 만 한다. 쓰기 경로가 없다.
노드의 `onReceive` 는 **메시 내부 메시지**(HB/LG/DV/DC)만 처리한다.

### 만들려면 건드려야 하는 것

| # | 대상 | 작업 | 위험 |
|---|---|---|---|
| 1 | `gateway/serial_source.py` | 시리얼 **양방향화**. 현재 `iter_lines()` 는 제너레이터라 쓰기 핸들이 밖으로 안 나온다 — 구조 변경 | 읽기 루프와 쓰기가 같은 포트를 공유. 타이밍 잘못하면 **읽기가 막힌다** = 사망 패킷 유실 |
| 2 | `gateway/gateway.py` | 프레임마다 경보 대상 id 목록을 만들어 하향 명령 생성 | 틱마다 쓰면 시리얼이 포화된다. 변화가 있을 때만 보내는 로직 필요 |
| 3 | `firmware/node/node.ino` (브리지) | 시리얼에서 한 줄 읽어 파싱 → `mesh.sendBroadcast` 로 중계 | **루프 블로킹**. 브리지 루프에 `Serial.readStringUntil` 을 넣으면 메시 처리가 밀린다. 8/30 에 `readTemp()` 블로킹으로 이미 한 번 겪었다 |
| 4 | `firmware/node/node.ino` (전 노드) | 새 타입(예: `AL`) 수신 처리 + LED 3색 + 해제 조건 | `MESH_JSON_CAPACITY` 재검토. 8/30 에 송·수신 버퍼 불일치로 PARSE_FAIL 을 겪었다 |
| 5 | 전 노드 | **16개 재플래시** | 굽기 검산·mid 확인 재실행 |
| 6 | 문서 | 덱·Q&A·스펙 문서에서 (가)/(나) 구분 재정리 | 덱은 v9 동결이라 **재조판이 필요** |

### 위험 요약 — 마감 3일에 이걸 하면

- **가장 큰 위험은 3번(브리지 루프 블로킹)이다.** 브리지가 밀리면 **사망 패킷이 유실**되고,
  그건 이 프로젝트의 핵심 산출물이 깨진다는 뜻이다. 얻는 것(LED 색 하나)보다 잃는 것이 크다.
- 5번 재플래시는 t80 교정 때 어차피 하므로 그 자체는 추가 비용이 아니다.
- 6번 때문에 **덱 동결이 풀린다.** 지금까지 v9 까지 온 조판 작업을 다시 열어야 한다.

### 대안 — 코드를 건드리지 않고 같은 효과를 내는 방법

영상에서 **대시보드 화면과 판을 split-screen 으로 붙인다.**
경보는 화면 쪽에서 뜨고, 판에서는 노드가 실제로 죽는다. 두 개가 같은 시각에 움직이는 것을
한 프레임에 담으면, LED 색을 바꾸지 않고도 「죽음 → 추정 → 경보」 인과가 보인다.
`docs/cowork/시연영상_스토리보드_불사.md` 의 컷5~8 이 이미 split-screen 구성이다.

**판단은 사용자 몫이다. 여기서는 비용만 적었고 아무것도 구현하지 않았다.**
