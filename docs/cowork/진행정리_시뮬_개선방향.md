# 진행 정리 — 시뮬레이션 & 개선방향 (실무용어 + 쉬운 풀이)
### 화중생련 「불사」 / 부품 대기 중 소프트웨어 진행 요약본

> 표기 규칙: **실무용어**(= 쉬운 풀이). 읽으면서 용어에 익숙해지게.

---

## 0. 전체 그림 (한 눈)

부품(ESP32 등)이 오기 전에, **하드웨어 없이 컴퓨터 안에서 핵심 알고리즘을 먼저 만들고 검증**했다.
순서: ① 시뮬레이터로 뇌(알고리즘) 검증 → ② 어려운 상황에서 강건성 측정 → ③ 측정 정직화 → ④ 발표용 대시보드 → ⑤ 펌웨어 준비(하드웨어 없이 가능한 부분).
결과: **알고리즘은 검증 완료. 남은 건 검증된 로직을 실물 ESP32로 옮기는 것(부품 도착 후).**

---

## 1. 시뮬레이터 (#1) — 뇌를 먼저 만든다

**한 것:** ESP32 없이, **네트워크 시뮬레이터**(network simulator = 가짜 노드들이 컴퓨터 안에서 도는 프로그램)로 4대 기능을 구현·검증.
- **자가치유 라우팅**(self-healing routing = 노드가 죽어 길이 끊기면 자동으로 우회로를 다시 짜는 것)
- **임종신호**(Last-Gasp = 노드가 임계온도 넘겨 죽기 직전 쏘는 마지막 패킷)
- **통신두절/파괴 구분**(cross-verification = 조용해진 노드가 진짜 죽음인지 잠깐 끊김인지 이웃 여러 개가 확인)
- **★ 고장 패턴 추정**(failure-pattern estimation = 죽은 노드들의 좌표·시각으로 불의 방향·속도를 역산)

**핵심 알고리즘 = 도착시각 지도**(arrival-time field): 노드가 죽은 시각 = 불이 그 지점에 도착한 시각. 흩어진 (위치, 죽은시각)에 **최소제곱**(least squares = 점들에 가장 잘 맞는 면을 긋는 수학)으로 **기울기(gradient)**를 구하면 → **진행 방향 = 기울기 방향, 속도 = 1/기울기크기.** 딥러닝 아님(가벼운 계산).

**결과(정상 조건):** 방향오차 2.12°, 속도오차 0.10%, 전달률 92.3%, 오탐 0%.
**밀도 실험:** 노드 9→25개로 늘리니 방향오차 4.32°→1.23°. (많을수록 정밀 = "성기지만 밀도 올리면 정확" 논리의 근거)

## 2. 스트레스 테스트 (#2) — 일부러 어렵게 만들어 한계선 찾기

**한 것:** 쉬운 조건 말고 **어려운 상황**을 7가지 만들어(바람 요동, 돌풍, 방사형 확산, 노드 배치 흔들림, 통신 노이즈↑, 저밀도, 복합) 각각 **여러 강도 × 여러 시드**로 돌려 성능이 어떻게 무너지는지 측정.
- **시드**(seed = 난수 씨앗. 고정하면 같은 결과 재현) / **강건성**(robustness = 험한 조건에서도 버티는 정도)

**핵심 발견 — 작동 한계선(operating envelope):**
- **오탐 방어**(false positive = 안 죽었는데 죽었다고 오판)는 통신두절 확률 0.20에서 처음 뚫림(그전엔 0%).
- **속도 추정**은 노드 9개(초저밀도)에서 붕괴(오차 34.5%), 12개부터 안정 → **"12노드 이상 운용" 근거.**
- **방향**은 바람 요동에 제일 약함, **속도**는 저밀도·돌풍에 제일 약함.

**규율:** 결과가 나빠도 파라미터를 유리하게 안 고침(measure-honest = 있는 그대로 측정). 그래야 "데모에만 맞춘(overfitting)" 함정을 피함.

## 3. 에러바 수선 (#2b) — 정직한 수치로 교정

**문제였던 것:** #2에서 바람이 **고정 파형 하나**라 시드를 바꿔도 추정오차가 안 변해 **에러바**(error bar = 수치의 ± 불확실성)가 가짜로 0에 가깝게 나옴.
**수선:** 바람을 **시드마다 다른 실현**으로 바꿔 에러바를 진짜 통계로 만듦.
**정직한 재특성화(중요):** 랜덤 바람을 넣으니 **속도 오차가 실제론 꽤 큼**(강풍서 20~30%). 즉 **방향·위치는 견고, 속도는 취약** — #2의 낙관치를 교정.
→ **발표 원칙: "방향은 신뢰, 속도는 보수적으로(안전마진)."** (0.1% 같은 숫자를 우기면 심사서 깨짐)

## 4. 웹 대시보드 (#3) — 발표·시연용 관제 화면

**한 것:** 시뮬이 뿜는 **스냅샷**(snapshot = 매 순간 전체 상태 사진)을 받아 재생하는 **자체완결 HTML 플레이어**(서버 없이 브라우저로 열림). 노드 생사·자가치유 경로·참/추정 화선·대피경보를 재생/일시정지/탐색.
**stock vs ours 토글:** 기존 방식(연결성만)과 우리(화선 벡터·ETA 추가)를 나란히 비교 → 차별점 시각화.

## 5. 펌웨어 포팅 준비 (#4 Phase A) — 하드웨어 없이 가능한 부분

**분담:** 노드 = **펌웨어**(firmware = 칩에 직접 구워 넣어 하드웨어를 굴리는 SW), C/C++ (Arduino-ESP32 + **painlessMesh** = 자동으로 그물망 만들고 우회하는 메시 라이브러리). 게이트웨이 = 라즈베리파이(Python).
**핵심 성과:** 게이트웨이가 **시뮬의 추정기(estimator) 코드를 그대로 재사용** → 모의 데이터로 돌렸더니 방향 2.115°·속도 0.096%가 **시뮬 직접값과 완전 일치.** (알고리즘을 실물 파이프라인에 그대로 이식 가능함을 증명)
**남은 것:** 펌웨어 컴파일 확인은 **Wokwi**(wokwi.com = 브라우저 ESP32 시뮬레이터)에서 사용자가, 실물 메시·통합은 **부품 도착 후.**

## 6. 핵심 개선방향 / 정직한 한계 (앞으로 지킬 것)

1. **방향은 신뢰, 속도는 보수적으로** — 대피 경보엔 안전마진(속도 상한 가정)으로 더 일찍 대피.
2. **12노드 이상 운용** — 저밀도 속도붕괴 실측이 근거. 데모는 실물 16 + 시뮬 확장.
3. **오탐 방어가 차별점** — "통신두절 vs 진짜 파괴" 구분(다중 이웃 + 온도 교차검증). 여기가 기존 메시와 다른 지점.
4. **재라우팅 실지연은 실물에서 첫 실측** — 시뮬의 "100ms"는 사실 틱(tick=시간 한 칸) 값이라 하드웨어 성능 아님. 발표선 "시뮬상 즉시, 실측은 포팅에서".
5. **의성은 동기·삽화만** — "그때 우리가 있었으면 막았다"식 반사실 주장 금지. 근거는 일반 산불 대응 공백↔기능 매핑.
