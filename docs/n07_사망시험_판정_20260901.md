# ★★★ 추가 — 2시간 소크가 밝힌 손실 기전 (2026-09-01 02:40)

## 1. 브리지가 노드 하트비트를 **초당 1.3개**만 내보낸다

깨끗한 구간(t=70초 이후, 깨진 줄 0건)에서 브리지가 뱉는 노드 HB 는 **약 0.76초에 하나**,
그것도 15대를 **돌아가며** 하나씩이다. 노드 15대는 초당 15개를 보낸다.

| | 실측 |
|---|---|
| 노드가 보내는 양 | 15대 × 1 Hz = **15개/초** |
| 브리지가 내보내는 양 | **≈1.3개/초** |
| 그래서 노드당 재등장 주기 | **15~21초** (ms 간격 중앙값 21.0초) |
| 노드별 도착률 | **5~9%** |

노드가 게으른 게 아니다. 같은 노드의 `ms` 간격 **최솟값이 정확히 1.00초**다 —
연속된 1 Hz 하트비트가 실제로 도달한 순간이 있다는 뜻이고, 노드 송신은 정상이다.

## 2. 브리지 자신의 loop() 가 **0.5초 주기**로 돈다

브리지 자기 HB 는 무선을 거치지 않는다. 그런데도 간격이 **1.519초**다(601개 중 575개).
`HEARTBEAT_MS` 는 1000이므로, 루프가 빠르면 1.00초여야 한다. 1.52 ≈ 3 × 0.507 이므로
**loop() 한 바퀴가 약 0.5초**다. 브리지의 자기 HB 도착률 65%는 여기서 그대로 나온다
(1.000 / 1.519 = 65.8%).

> 무엇이 0.5초를 먹는지는 **미확정**이다. `readTemp()` 의 블로킹은 9비트라 94 ms 이고
> (`node.ino:283`), `SENSE_MS` 는 500이다. `mesh.update()` 가 유력하지만 펌웨어를
> 계측하지 않고는 못 가른다 — **굽기는 사람이 한다**(강령 §3).

**나는 (다)를 권한다.** 다만 **헌장 §1 동결값과 D-069 시각표에는 손대지 않는다** —
`HEARTBEAT_MS` 는 동결 목록(80℃ · 20cm · 4×4)에 없고 사망 시각표와도 무관하다.
다만 `SILENCE_TIMEOUT_MS(3000)` 가 하트비트 3회분을 전제하므로 **함께 봐야 한다**
(5초 주기로 바꾸면 침묵 판정이 하트비트 0.6회분이 되어 오탐이 난다).

> **굽기는 사람이 한다.** 나는 밤새 읽기와 계측만 했고 펌웨어·배선·전원은 건드리지 않았다.

## 6. 못 가른 것 — **「브리지가 못 받는다」와 「받고도 안 찍는다」**

둘은 대책이 다르다. 가르려고 사망투표(DV) 유무를 보려 했으나 **그 방법은 성립하지 않는다.**

    node.ino:453   bool silent = (now - n.lastHeard) > SILENCE_TIMEOUT_MS;
    node.ino:454   bool hot    = (n.peakTemp >= WARN_TEMP_C) || (curTemp >= WARN_TEMP_C);
    node.ino:455   if (silent && hot && !n.voted) { ... sendVote(...) }

투표는 `silent` **그리고** `hot` 일 때만 나간다. 소크는 전부 실온(24~26℃)이므로
`hot` 이 거짓이라 **침묵과 무관하게 투표가 0건인 것이 정상**이다. DV 가 0인 것은
브리지의 수신 상태에 대해 **아무것도 말해 주지 않는다.**

가르려면 펌웨어에 수신 카운터를 넣어 재굽어야 한다 → **사람이 할 일.**

### ★ 그런데 이 코드 자체가 위험을 하나 더 드러낸다

투표가 나가려면 **이웃이 그 노드의 뜨거운 하트비트를 먼저 받아 두어야** 한다
(`n.peakTemp >= 60℃`). n07 은 21초 만에 25℃ → 105℃ 로 갔다. 이웃이 그 구간에서
하트비트를 **한 개라도** 받았어야 하는데, 지금 도착률에서는 **0개일 수 있다.**

즉 **주 경로(임종신호)와 예비 경로(침묵 투표)가 같은 원인으로 동시에 막힌다.**
예비 경로가 주 경로를 구해 주지 못한다 — n07 에서 실제로 둘 다 실패했다.
