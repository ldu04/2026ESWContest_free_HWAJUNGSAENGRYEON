> 쪽에서 **풍속별 τ 실측**이 진행된다. 이 지시서는 **그와 병행 가능한(하드웨어 불필요) 작업 4건**이다.
>
> **강령(전 작업 공통 — 상세는 `강령_v5_수치무결성_예측규율.md`):**

있는 것들(D-047~D-052, 어댑터, 펌웨어 수정 2건, 강령 v5, BUILD.md)은 잃으면 복구 비용이 매우 크다.

- 논리 단위로 나눠 커밋(기록 / 어댑터 / 펌웨어 / 스윕 결과 / 문서)
- 커밋 메시지에 대응 D 번호 명시

**추가 지시(작업 중 수신):**
- **머지는 미루지 말고 즉시.** 새 세션이 master를 보면 #2e 이전 상태가 보여 **이미 한 작업을
  다시 하거나 덮어쓸** 위험. fast-forward라 한 줄이면 끝난다. 여유 되면 **태그**도.
- **단일 커밋을 다시 쪼개지 말 것.** 소실 방지는 이미 달성됐고, 단계별 기록은 커밋 히스토리가 아니라
  **DECISIONS.md D-026~D-052**가 담당한다(판정 근거까지 있으니 그쪽이 낫다). 재분할은
  `config.py`·`engine.py`·`node.py`에 여러 단계 knob이 섞여 **원리적으로 불가**하고,
  깨끗한 상태를 흔들 위험만 있다. 남은 한 달은 τ 실측에 쓴다.
- **집계 CSV(`summary_*`)가 저장소에 있는지 확인.** 강령 §A-8("제출 직전 모든 수치를 원자료와
  1:1 대조")은 근거 파일이 저장소에 있어야 성립한다. raw(대용량)는 제외해도 되지만 집계는 필수.

## [2] 속도·ETA 절대값 표

**문제:** 2.K §4가 지터 취약성을 **배율**로만 보고했다(속도 1.2~23배 vs 방향 196배).
**기준선이 다르면 배율은 오해를 부른다.**

수학적으로도 확인된다(`명세_FailurePattern_수학적정식화.md` §6): 방향 각오차와 속도 상대오차는
**둘 다 1/|∇T|에 비례**해 등방성 노이즈 아래서 **절대 민감도가 비슷**하다. 배율 차이는 방향의
기준선이 0.345°(≈0.006 rad)로 극히 작고 각도가 90°에서 포화하기 때문에 생기는 착시일 가능성이 크다.

**요청:** 2.K §4 원자료에서 **절대값 표**를 산출.
- 축: τ ∈ {0, 2, 5, 10, 11, 20, 30, 50, 78.5, 100} s × 모드(균일/지터 σ=30 %) × 전선(S1/S2a10/S2a20)
- 값: **속도오차(% 및 m/s 절대), ETA오차(초)** — 평균 ± 표준편차
- 함께: 각 셀의 **방향오차(도)** 를 같은 표에 넣어 세 지표를 나란히 비교 가능하게
- **배율 열을 넣을 경우 반드시 분자·분모를 함께 표기**(강령 §A-3)

**판정:** 속도·ETA가 실용선(기존 E3x2 밴드 기준, 임의 변경 금지)을 어느 τ에서 벗어나는지.
결론 문장은 쓰지 말고 표와 플래그만.

## [3] 링크두절 vs 실제사망 판별 — 커버리지 확인 (단정 금지, 현황 파악부터)

**문제 제기:** 우리 전제는 **"노드 침묵 = 화재 도착"**(명세 §2의 가정 A5)이다. 그러나 침묵의 원인은
최소 넷이다: **(a) 소손 (b) 링크 두절 (c) 전원 소진 (d) 크래시·리부팅.** 가짜 사망은 도착시각장에
잘못된 표본을 주입해 **적합 전체를 오염**시킨다. τ가 "언제 죽었나"의 정확도 문제라면, 이건
**"죽은 게 맞나"의 문제**라 더 근본적이다.

**단, 이미 부분 커버돼 있을 가능성이 높다.** D-003에 링크 일시두절이 난수 환경으로 들어가 있고,
회귀 지표에 fp(오탐)가 있으며, 2.D에 비화재사망 방어가 있다.
**그러므로 "구멍이다"라고 단정하지 말고 현황부터 확인할 것.**

**작업 순서:**
1. **현황 조사** — 현재 시뮬·펌웨어·게이트웨이에서 (b)(c)(d)가 각각 어디까지 모델링·방어·검증돼
   있는지 조사해서 표로. 특히:
   - 시뮬의 링크 두절 모델이 **일시적 두절만**인지, **영구 두절(노드는 살아있는데 통신만 끊김)**도
     포함하는지
   - 펌웨어의 침묵 감지(3 s) + 투표가 (b)와 (a)를 실제로 구분하는지, 아니면 침묵을 곧 사망으로
     승격하는지
   - 배터리 소진·크래시가 모델에 존재하는지
2. **부족분이 확인되면** 그때 전용 스윕 설계를 제안(이 지시서에서 미리 설계하지 않음 — 현황을
   모르는 상태의 설계는 낭비).
3. 결과는 **"커버된 것 / 부분 커버 / 미커버"** 세 칸으로 정직하게 분류.

## [4] 타원 전선 모델 — 문헌 기반 형상으로 곡률 한계 판정

**왜:** 현재 전선 모델은 직선과 **인위적으로 만든 곡률**(S2a10, S2a20)이다. 그런데
**S2a20은 τ=0에서도 방향오차 10.58°** — 이건 τ 탓이 아니라 **평면 적합의 곡률 한계**(명세 §9-1)다.
문제는 **실제 산불 전선이 그 정도로 굽는지를 우리가 모른다**는 것. 안 굽으면 무시해도 되는 한계이고,
그만큼 굽으면 우리 주장의 실제 구멍이다.

**범위 한정(중요):** 본격 물리 확산 모델(Rothermel 계열)은 **하지 않는다.** 연료 모델·수분·지형
데이터가 필요해 미검증 가정을 무더기로 추가하게 되고, "그 화재 모델은 검증했냐"는 질문이 τ 곡선
때와 똑같이 되돌아온다. 남은 기간에도 무리다. **대신 문헌에 정착된 단순 형상 모델만 쓴다.**

**4-1. 문헌 확인 먼저 (구현 전).**
바람이 있을 때 화재가 **대략 타원 형태로 성장**한다는 단순 모델(발화점이 타원의 초점 근처에
오는 형태)이 산불 거동 분야에서 널리 쓰인다. **다만 이 서술은 Cowork의 기억에 기반한 것이므로,
구현 전에 반드시 문헌으로 확인할 것:** 모델의 정확한 형태(장축/단축 비, 발화점 위치, 풍속 의존성) /
장단축비가 풍속에 따라 어떻게 변하는지 / 출처를 기록에 남길 것 /
**확인 결과 기억과 다르면 그대로 보고하고 문헌을 따를 것.**

**4-2. 전선 형상 생성기 추가.** 기존 전선 생성부에 **타원 성장 형상**을 옵션으로 추가.
`sim/estimator.py`는 건드리지 않는다. 풍속(또는 장단축비)을 파라미터로 두고, **바람이 셀수록
길쭉한 타원**이 되도록. 기존 S1/S2a10/S2a20은 대조군으로 유지.

**4-3. 곡률 정량화 — 이게 핵심 산출물.** 타원 전선의 **노드 스케일에서의 곡률**을 계산해서,
인공 곡률 케이스(S2a10, S2a20)와 **같은 척도로 비교**. 즉 "타원 전선의 곡률은 S2a10과 S2a20 사이
어디에 위치하는가"를 수치로 답할 것. 곡률은 부위(선단 vs 측면)에 따라 다르므로 **부위별로** 낼 것.
**노드 격자가 전선의 측면을 지나는 경우가 최악일 수 있음.**

**4-4. 추정 성능 측정.** 타원 전선 조건에서 방향오차·속도오차·추정 가능률을 산출.
τ 축도 함께(최소 {0, 11, 78.5} s). 기존 S1/S2a10/S2a20 결과와 **같은 표에** 나란히.

**Cowork 사전등록 예측 — 결합 명세 먼저(강령 §B-2):**
> **결합:** 풍속↑ → (1차) 타원이 길쭉해져 선단 곡률↑ → 방향오차↑ 가능. **(2차)** 그런데 풍속↑는
> 확산속도 s↑도 뜻하고, s↑ → |∇T|↓ → 명세 §6에 따라 δφ, δs/s 둘 다 ↑. **(3차)** 동시에 s↑는
> 이웃 사망 간격 h/s↓를 뜻해 창 요건(§9-2)에는 유리.
> **예측 [유추 등급, 신뢰도 낮음]:** 타원 전선의 노드-스케일 곡률은 S2a20보다 완만해 방향오차가
> 10.58°보다 작을 것. 단 선단부에서는 국소적으로 클 수 있음.
> **이 부류(지연-기하 결합)에서 Cowork 예측은 지금까지 6번 중 4번 빗나갔다. 측정치를 그대로 보고할 것.**

**산출:** 원자료 + 그래프 + 곡률 비교표 + 예측 어긋난 지점 플래그.
**결론 문장은 쓰지 말 것**(해석은 Cowork).
