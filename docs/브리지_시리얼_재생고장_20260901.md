# 브리지 시리얼 「재생 고장」 (2026-09-01)

## 증상
브리지 포트에서 **똑같은 조각 하나가 초당 96회 반복**된다.

    b'"fake":0,"nt":867.843125}'   × 1918회 / 20초

`nt`(메시 시각)가 **867.843125 에 얼어붙어** 있다. 펌웨어는 얼어붙은 시각을 1918번 찍을 수
없다 — **옛날 한 줄이 재생되는 것**이다. 동시에 정상 프레임도 43줄/20초 들어온다.
즉 **진짜 데이터와 재생 쓰레기가 섞여** 나온다.

측정 초기에는 6초에 **445 kB** 가 나왔다. 115200 baud 의 물리 한계는 6초에 69 kB 이므로
**전송이 아니라 재생임이 산술로 증명된다.**

## 영향
- 리허설 1회차에서 게이트웨이가 **23분간 유효 프레임 0건**이었던 직접 원인.
  게이트웨이는 조용히 살아 있었고 아무 경고도 내지 않았다.
- 고장 중에도 정상 프레임이 **초당 2.15개** 들어온다(기대 3.2개) → **약 1/3 손실**.
  하트비트는 반복되니 견디지만, **사망 신호(LG/DC)는 단발**이라 이 손실률은 치명적이다.

## 조치
| 조치 | 결과 |
|---|---|
| 포트 닫았다 열기 | 효과 없음 |
| `stty` 재설정 | 효과 없음 |
| **CP210x 드라이버 언바인드/리바인드** | 74 kB/s → 0.4 kB/s 로 정상화. **약 20초 뒤 재발** |
| USB 물리적 재삽입 | **실패 — 즉시 재발** |
| 파이 재부팅 | **실패 — 재부팅 직후에도 재발** |
| **브리지를 노트북에 연결** | **★ 성공 — 20초 25줄 전부 정상, 깨진 줄 0** |

## 감시 (재발해도 사람이 알게)
게이트웨이에 **폭주 감시견**을 넣었다(`gateway.py`). 10초 창에서 깨진 줄이 정상의 3배를
넘고 표본이 50줄 이상이면 stderr 로 경고하고 **USB 재삽입을 지시**한다.
침묵 감시견(20초 무데이터)만으로는 이 고장을 못 잡는다 — **바이트는 쏟아지기 때문**이다.

## 결론 — 파이 USB 경로의 결함이다

가장 명확한 증거: 브리지 **부팅 메시지**의 마지막 줄 `entry 0x400805b4` 가 찍힌 뒤,
그 꼬리인 `5b4` 가 **5289회 반복**됐다. 반복되는 내용이 펌웨어가 무엇을 찍었느냐와
무관하게 **「직전 조각의 꼬리」**라는 점이 핵심이다. 펌웨어는 이런 출력을 만들 수 없다.
같은 브리지 보드를 **노트북에 꽂으면 깨진 줄이 0** 이므로 보드도 무죄다.

## ★ 정정 (같은 밤, 1시간 뒤) — **파이 전용 문제가 아니다**

위 결론은 **노트북 측정 1회**에 근거했는데, 그 측정은 포트를 열며 **보드를 리셋한** 직후였다.
리셋 없이 다시 재자 노트북에서도 **60초에 깨진 줄 16,270개**가 나왔다. 그 직후 같은 포트를
15초씩 두 번 더 재니 **정상 34줄 · 깨진 0줄**이 두 번 다 나왔다.

정리하면:
- 고장은 **간헐적**이다. 리셋 직후에는 잠잠하고, 시간이 지나면 터진다.
- **호스트를 바꿔도 따라온다**(파이·노트북 양쪽에서 관측).
- 따라서 의심 대상은 호스트가 아니라 **브리지를 따라다니는 것** — USB 케이블 또는 보드의 커넥터다.
  (n01 때 「고장은 점퍼선이 아니라 보드를 따라간다」로 원인을 가른 것과 같은 논리다.)

**다음 시험**: 브리지의 **USB 케이블만 교체**하고 리셋 없이 60초 측정한다.
- 깨끗해지면 → 케이블 불량. 끝.
- 그대로면 → 브리지 보드의 USB 커넥터/USB-UART. **다른 보드에 99 를 다시 굽는다**(약 190초).

## 결정 [D-075] (정정 전 판단 — 아래 정정을 함께 볼 것) — 촬영은 **노트북에서** 돌린다

- 게이트웨이 실행 위치를 파이 → **노트북**으로 옮긴다. `deploy_config.json` 해시가
  양쪽 동일(`3828925d8bf4e461`)이므로 산출물은 달라지지 않는다.
- **파이의 USB-C 접촉이 불안정하다**(사용자 확인). 이 밤에 파이가 한 번 재부팅됐고,
  전원 흔들림이 USB 호스트 상태를 망가뜨렸을 가능성이 크다. **촬영 전까지 파이는 건드리지 않는다.**
- 파이는 예비 경로로만 남긴다.
