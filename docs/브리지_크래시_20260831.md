## 1. 사망 정보는 **1회만** 전송된다 — (a)다

지시받은 질문: 사망 상태가 (a) 1회만 전송되는가, (b) 하트비트에 계속 실려 재전송되는가.

**(a)다. 그리고 재전송 경로가 어디에도 없다.**

| # | 사실 | 코드 |
|---|---|---|
| 1 | **DEAD 노드는 하트비트를 아예 안 보낸다** | `firmware/node/node.ino:121` `if (state == DEAD) return;` |
| 2 | 임종신호(LG)는 전이 직후 **1회**, 재전송 잠금 | `node.ino:362` `sendLastGasp();` · `node.ino:135` `lastGaspSent = true;` |
| 3 | 관측자는 **1표만** 던진다 (`!n.voted` 조건) | `node.ino:394` `n.voted = true;` |
| 4 | 루트는 DC를 **1회만** 낸다 | `node.ino:174` `if (!NODE_IS_ROOT \|\| confirmed.count(suspect)) return;` |
| 5 | 루트 집계 상태가 **RAM 전용** → 재부팅 시 소실 | `node.ino:68-69` `std::map<int,std::set<int>> votes; std::set<int> confirmed;` (+`lgNtCache`·`lastNtCache`·`hadLastGasp`·`posCache`) |

**③이 결정적이다.** 브리지가 살아나도 이웃은 `n.voted` 래치 때문에 **다시 투표하지 않는다.**
즉 **복구 경로가 원리적으로 없다.**

### 게이트웨이의 중복 사망 처리 — **이미 있다**

`gateway/fw_adapter.py:380`

```python
elif typ == "DC":
    if nid is not None and nid not in self.confirmed:
        self.confirmed.add(nid)
```

같은 id 의 DC 가 여러 번 와도 **첫 번만 반영**한다.
**→ (b)로 바꿔도 게이트웨이는 손댈 필요가 없다.** 이건 (b) 전환의 비용을 크게 낮춘다.

## 3. ★ 화면에서 어떻게 보이나 — **「판은 빨강, 화면은 초록」이 맞다**

| 단계 | 코드 | 결과 |
|---|---|---|
| 노드가 임계를 밟음 | `node.ino:360` `state = DYING; setLed();` | **판 위 LED 즉시 빨강** |
| 게이트웨이가 LG 를 받음 | `fw_adapter.py:357` `if self.state.get(nid)=="ALIVE": self.state[nid]="DYING"` | 화면 **주황** |
| 게이트웨이가 DC 를 받음 | `gateway.py:246` `self.state[uid] = "DEAD"` | 화면 **회색 + X 마커** (`app.js:145`) |
| 대시보드 색 | `app.js:9` | `ALIVE #2ca02c 초록` / `DYING #ff9021 주황` / `DEAD #3a3f45 회색` |

**`DEAD` 는 오직 DC 로만 확정된다**(`gateway.py:231` 주석 「DEAD는 DC로만 확정」).

### 그래서 유실되면

LG 와 DC 는 3~5초 간격으로 연달아 나가는데 **맹점이 27초**다. 죽는 순간이 맹점 안에 들어가면
**둘 다 유실된다.** 그 노드는 이후 HB 를 영영 보내지 않으므로 상태가 갱신되지 않는다.

    → 대시보드에 **초록(ALIVE)으로 얼어붙는다.**
    → 판 위 LED 는 **빨강**이다.
    → split-screen 촬영에서 **모순이 그대로 찍힌다.**

**이것이 이 문제를 촬영 저해로 만드는 진짜 이유다.** 추정 정확도만 보면 결측 1개는
중앙값 1.62° 로 견딜 만하다(`docs/추정기_강건성_20260831.md` §b). **그러나 화면이 거짓말을 한다.**

## 4. 원인 — `err=4` 는 힙 고갈이다. 힙 궤적을 잡았다

브리지에 `ESP.getFreeHeap()` / `getMinFreeHeap()` / **`getMaxAllocHeap()`** 을 5초마다 찍게 했다
(`node.ino` `logHeap()` — 숫자만 출력해 계측이 문제를 키우지 않게 했다).

**크래시 직전 궤적 (재굽기 후 첫 회차):**

| t (s) | free (B) | min_free (B) | **max_alloc (B)** |
|---|---|---|---|
| 정상 구간 | 150,000 ~ 200,000 | — | **110,580** |
| 134.1 | 84,788 | 78,988 | 40,948 |
| 139.4 | 78,836 | 74,916 | 40,948 |
| **144.8** | **63,416** | **57,564** | **40,948** |
| **152.62** | — | — | — | ← **크래시 `rst:0xc SW_CPU_RESET`** |

**★ 읽는 법:** 총량(`free`)보다 **`max_alloc`(연속으로 잡을 수 있는 최대 블록)**이 중요하다.
`NoMemory` 는 총량이 아니라 **연속 블록**이 모자랄 때 난다. 정상 110 kB 이던 것이
**41 kB 로 주저앉은 채 회복되지 않았고**, 그 상태에서 힙이 15초 만에 195 kB → 63 kB 로 빠졌다.

| 바꾼 것 | 근거 |
|---|---|
| **`TOPO` 의 `subConnectionJson()` 을 기본 OFF** (`TOPO_FULL_SUBTREE 0`) | 5초마다 **최대 577자 String** 을 새로 만들었다(30분에 338회 실측). 그런데 **게이트웨이는 TOPO 를 쓰지 않는다** — 모르는 타입이라 `dropped_types` 로 세고 버린다. 힙이 모자란 판에 쓰지도 않는 문자열을 만드는 것은 순수 손해다. `n_peers`(정수)는 남겼다 |

## 6. 하트비트 주기 — 늘리면 무엇이 따라오나 (평가만, 굽지 않았다)

### 현재

| | 값 | 코드 |
|---|---|---|
| `HEARTBEAT_MS` | **1000** | `firmware/node/config.h:88` |
| `SILENCE_TIMEOUT_MS` | **3000** | `config.h:89` |
| `K_CONFIRM` | 3 | `config.h:90` |
| **실측 송신 주기** | **1.518 s** | 브리지 자기 HB 간격 중앙값 (설정보다 **52% 느리다**) |

### 늘렸을 때 — 좋아지는 것

- **트래픽이 주기에 반비례해 준다.** 2초로 하면 절반, 3초로 하면 1/3.
  브리지의 `onReceive` 호출과 `Serial.println` 횟수가 그만큼 줄어 **힙 압박이 완화될 수 있다.**
- 무선 혼잡이 줄어 **노드→루트 도착률**이 오를 여지가 있다(11대에서 11.5~15.1%까지 떨어졌다).

### ★ 반드시 같이 바꿔야 하는 것 — 안 그러면 가짜 사망이 난다

`SILENCE_TIMEOUT_MS` 는 **하트비트 주기의 배수**로 정해져야 한다.
지금은 3000 / 1000 = **3배**다. 그런데 **실측 주기 1.518초 기준으로는 1.98배**뿐이다 —
**연속 2개만 못 들어도 투표가 시작되는 아슬아슬한 설정이다.**

    HEARTBEAT_MS 를 2000 으로 올리면  → SILENCE_TIMEOUT_MS 를 6000 이상으로
    HEARTBEAT_MS 를 3000 으로 올리면  → SILENCE_TIMEOUT_MS 를 9000 이상으로

**안 올리면 살아 있는 노드가 전부 「침묵」으로 판정되어 대량 오탐이 난다.**

### 사망 판정에 주는 영향 — **시각은 안 밀린다**

- **사망 시각은 죽은 노드가 각인한 `nt`(LG 시각)를 쓴다**(제약③, `node.ino:180-186`).
  침묵 문턱을 늘려도 **death_t_est 는 그대로다.** 늦어지는 것은 **확정(DC) 시각**뿐이다.
- 대본 B 의 인접 사망 간격이 **약 328초**다. 확정이 6~9초 늦어지는 것은 **무시할 수준**이다.
- 다만 **런 끝의 마지막 노드들**은 확정이 더 밀려 `K_CONFIRM` 미달로 남을 수 있다
  (이미 드라이런에서 마지막 3개가 미확정이다). 침묵 문턱을 늘리면 **그 꼬리가 조금 길어진다.**

### 비용

**노드 17대 전량 재굽기 ≈ 70분** (플랜 C 기준 대당 약 190초 + 검증).

> **★ 전략적 판단:** §1 의 (a)→(b) 수정도 **같은 재굽기 비용**을 요구한다.
> **노드를 다시 구울 거라면 두 가지를 한 번에 해야 한다.** 따로 하면 70분을 두 번 쓴다.

## 8-1. ★ 「0회」가 아니다 — 내 집계가 틀렸던 것을 정정한다

처음에 「크래시 0회」로 셌는데 **틀렸다.** 내 집계 함수가 `abort()` 와 `Guru Meditation` 만
찾고 **태스크 워치독 경로를 놓쳤다.** 실제로는 1회 리셋됐다.

## 8-2. 남은 1회의 전체 체인 — 힙 계측이 처음으로 잡아냈다

    t=144.76  {"type":"HEAP","free":63416,"min_free":57564,"max_alloc":40948,"peers":11}
                                                            ↑ 정상 110,580 → 40,948 로 붕괴
    t=147.06  ERROR: routePackage(): parsing failed. err=4, total_length=180
    t=148.08  ERROR: routePackage(): parsing failed. err=4, total_length=178
    t=152.36  E task_wdt: Task watchdog got triggered.
              E task_wdt:  - async_tcp (CPU 0/1)          ← ★ 굶은 태스크
              E task_wdt: Aborting.
    t=152.61  Rebooting... → rst:0xc (SW_CPU_RESET)
    t=153.72  {"type":"HEAP","free":199852,"min_free":199800,"max_alloc":110580,"peers":0}
                                                            ↑ 재부팅 후 완전 회복

**읽는 법:** 힙 총량보다 **`max_alloc`(연속 최대 블록)**이 먼저 무너진다.
110 kB → 41 kB 로 떨어진 뒤 `err=4 NoMemory` 가 나고, 그 여파로 `async_tcp` 태스크가
워치독을 못 치면서 리셋된다. **원인은 그대로 힙(단편화)이다.**

## 8-3. ★★ 위험 구간은 **메시 형성 직후**다 — 절차로 막을 수 있다

| 회차 | 리셋 시각 |
|---|---|
| 수정 전 | 149 s · **524 s · 748 s** ← 정상 운용 중에도 났다 |
| **수정 후** | **152 s 뿐** ← 그 뒤 27분은 조용하다 |

수정 후에 남은 1회는 **기준선 확정(t=120s) 직후**, 즉 11대가 한꺼번에 붙는 구간이다.
**정상 운용 중 크래시는 사라졌고, 형성 구간의 1회만 남았다.**

### → 절차에 반영할 것 (§0-0 전원 재인가 규칙과 짝이 된다)

**전원을 껐다 켠 직후가 가장 위험하다.** 그런데 §0-0 은 「매 런 직전 전원 재인가」다.
**그대로 하면 런을 가장 위험한 순간에 시작하게 된다.**

    전원 재인가 → **3분 기다린다**(메시 형성·안정) → 브리지 리셋 0건 확인 → 그 다음 런 시작

3분은 관측 근거가 있다: 리셋은 t=152 s(2.5분)에 났고 그 뒤 27분간 없었다.

## 8-4. 판정 — **노드 재굽기는 아직 필요 없다**

지시받은 기준: 「크래시가 0이 되면 노드 재굽기는 필요 없다.」

**엄밀히는 0이 아니라 1회다.** 그러나:

- 정상 운용 27분 무사고 · 남은 1회는 **형성 구간**이고 **절차(3분 대기)로 피할 수 있다.**
- 22분 런 기대 크래시: **2.2회 → 0회**(형성 구간을 런 밖으로 빼면).
- 이탈률도 55~71% 줄었다.

**→ 노드 17대 재굽기(70분)는 보류한다.** 다음 순서는 **16대 구성에서 같은 측정**이다.
16대에서 형성 구간 밖에도 크래시가 다시 나면, 그때 §1 의 (a)→(b) 수정과
하트비트 주기 변경을 **한 번에** 한다.
