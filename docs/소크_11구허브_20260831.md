## 1. 점호 — 기준선은 사람 목록이 아니라 브리지가 읽은 것으로 확정했다

사람 목록을 기다리지 않고, 시작 후 **150초 동안 합류한 집합**을 기준선으로 자동 확정했다.

| | |
|---|---|
| **합류 (기준선)** | **n09 · n10 · n11 · n14 · n15 · n16** + 브리지 — **노드 6대** |
| **미합류 후보** (= 전체 16 − 합류분) | n01 · n02 · n03 · n04 · n05 · n06 · n07 · n08 · n12 · n13 — **10대** |
| 합류 소요 | 브리지 2초, 노드 6대 전부 **10초 안에** 합류 |

### ★ 미확정 — 아침에 사람이 확인할 것

**어느 보드를 실제로 꽂았는지 모른다.** 그래서 「11대 중 5대가 합류 실패」인지
「애초에 6대만 꽂혔다」인지 **지금은 가를 수 없다.** 다만 객관적 단서가 하나 있다:

- 소크 시작 직전 **CP210x 데이터 포트가 8개** 열거됐다
  (`COM3` 브리지 · `COM6` `COM7` `COM8` `COM9` `COM10` `COM18` `COM19`).
- 즉 **데이터선이 붙은 노드가 7대**인데 **합류는 6대**다.
  → **데이터 포트에 꽂혀 있으면서 메시에 합류하지 않은 보드가 최소 1대 있다.**
- 소크 직전 배너를 읽어 확인된 것: `COM6 = n11` · `COM10 = n10` · `COM19 = n14`.
  `COM7` `COM8` `COM9` `COM18` 은 7초 안에 배너를 내지 않아 미식별이다.

**아침 확인법:** 소크가 끝난 뒤 `COM7` `COM8` `COM9` `COM18` 의 배너를 읽으면
어느 보드가 합류하지 않았는지 1분 안에 특정된다(합류분 n09·n15·n16 을 빼면 남는 하나).
소크 중에는 하지 않는다 — 포트를 열면 그 노드가 재부팅되어 측정이 오염된다.

## 2. ★ 핵심 — 침묵은 브리지 쪽이 아니라 **노드→루트 전달** 쪽이다

이것을 가르는 것이 이 소크의 가장 중요한 결과다.

| 근거 | 관측 | 뜻 |
|---|---|---|
| **브리지 자기 하트비트** | 이탈 **0회** · 간격 중앙 **1.518 s** · 최대 **1.553 s** | **브리지 루프는 멈춘 적이 없다.** 시리얼도 계속 나왔다 |
| 노드 하트비트 | 수율 **13 ~ 18%** · 간격 중앙 **4.6 ~ 5.3 s** | 노드 패킷이 루트에 **대부분 도달하지 않는다** |
| **DV(사망 투표)** | **0건** | 노드끼리는 **서로 잘 듣고 있다.** 안 들렸다면 서로 죽었다고 투표했을 것이다 |
| PARSE_FAIL | **0건** | JSON 버퍼 문제가 아니다 |

**→ 결론: 노드끼리의 링크는 살아 있고, 병목은 「노드 → 루트(브리지)」 구간이다.**
브리지가 죽거나 밀린 것이 아니다.

### 부수 관측 — 하트비트 주기가 설정값보다 **1.5배 느리다**

브리지 자기 HB 간격 중앙이 **1.518 s** 다. `config.h` 의 `HEARTBEAT_MS` 는 **1000** 이다.
같은 펌웨어가 모든 보드에 올라가 있으므로 노드도 같은 속도로 보내고 있을 것이다.
**이 자체가 별도의 발견이다** — 루프가 설계보다 52% 느리게 돈다.
원인은 **미확정**이다(추정하지 않는다). `readTemp()` 9비트 변환 94 ms 블로킹과
`SENSE_MS 500` 의 조합이 후보지만, 이 소크로는 가르지 못한다.

## 5. 촬영에 주는 함의 — ★ 아침에 판단이 필요하다

**시연 자체는 이 상태로도 될 가능성이 높다.** 시연의 입력은 하트비트가 아니라
**임종신호(LG)와 사망확정(DC)** 이고, 그건 사망 순간에 한 번 나가는 패킷이다.
그리고 노드끼리의 링크는 멀쩡하다(DV 0건이 그 증거다).

**그러나 두 가지가 걸린다:**

1. **게이트웨이의 침묵 기반 판정이 하트비트를 본다.** 수율 15%에서 게이트웨이가
   무엇을 하는지는 **이 소크로 측정하지 않았다.** 게이트웨이를 붙여 같은 조건에서
   한 번 돌려 봐야 안다.
2. **LG 도 같은 「노드 → 루트」 구간을 지난다.** 하트비트가 85% 유실된다면
   **LG 도 유실될 수 있다.** LG 를 한 번 놓치면 그 노드의 사망 시각을 잃는다.
   다만 펌웨어에는 LG 없이도 확정하는 최후 수단 경로가 있다(`node.ino` 의 `death_t_est`).
   **LG 유실률은 미측정**이다 — 이 소크에서는 아무도 죽지 않았으므로 잴 수 없었다.

**→ 아침에 t80 교정으로 노드를 실제로 죽여 볼 때, LG 가 도달하는지 반드시 같이 본다.**

## 7. n04 (NODE_ID 3) 특별 추적 — **판정 불가**

지시: 「합류·하트비트가 정상이면 *보드 정상, LED 재납땜만 필요*로 판정한다.」

**n04 는 메시에 합류하지 않았다. 하트비트 0건이다.**
따라서 **그 판정을 내릴 수 없다.**

**주의 — 이것을 「보드 불량」으로 읽으면 안 된다.** n04 는 **미합류 후보 10대 중 하나**이고,
애초에 꽂혔는지조차 모른다. 굽기 기록으로는 정상이다:

| | |
|---|---|
| 굽기 결과 | **PASS** (2026-08-31 04:00:30) |
| 배너 | `index 3 / role NODE / is_root=0 / thr=80C / warn=60C` |
| mid | 3179103081 · MAC `58:2a:bd:7d:43:68` |

**아침 확인 순서 (5분):**
1. n04 **한 대만** 노트북에 직결한다(허브 말고).
2. 배너에 `index 3` 이 나오는지 본다 → 펌웨어 확인.
3. 게이트웨이나 소크 감시기를 붙여 **HB 가 나오는지** 본다.
4. HB 가 정상이면 **「보드 정상 — LED 재납땜만 필요」** 로 확정한다.
   HB 가 없으면 그때 비로소 보드 문제다.

# ★★ 9. 55분 시점 — 가장 심각한 발견: 노드 시계가 통째로 되돌아갔다

## 무슨 일이 있었나

**실시각 t ≈ 2527 초에 노드 6대 전부가 mesh nodeTime 을 ~0 으로 되돌렸다. 브리지는 안 그랬다.**

    t=2546.79  n11  nt 3078.2 -> 20.5   (감소 3057.6)
    t=2547.56  n16  nt 3077.5 -> 20.8   (감소 3056.6)
    t=2548.33  n15  nt 3077.5 -> 20.9   (감소 3056.6)
    t=2549.10  n14  nt 3078.2 -> 21.0   (감소 3057.2)
    t=2575.78  n10  nt 3129.3 -> 48.6   (감소 3080.6)
    t=2576.54  n09  nt 3128.3 -> 48.7   (감소 3079.6)

검출 시각이 벌어진 것은 하트비트가 15%만 도착하기 때문이다. 각 노드의 `nt` 를 역산하면
**여섯 대 모두 실시각 2526 ~ 2528 초에 같이 재설정**됐다.

## ★ 이것은 uint32 랩어라운드가 **아니다**

| | |
|---|---|
| uint32 µs 랩 주기 | **4294.967 s** |
| 실제 감소량 | **3057 ~ 3081 s** |
| 사건 발생 시각 | 소크 시작 후 **42분** (71.58분이 아니다) |
| 브리지 | **되돌아가지 않았다** (`nt` 3304 s 로 계속 증가 중) |

**지금 노드는 브리지와 약 2531초 어긋난 시간축 위에 있다.** 55분 시점에서
브리지 `nt` = 3304 s, 노드 `nt` ≈ 773 s 다. 다만 **노드끼리는 0.85초 안에서 서로 일치**한다
(그 정도 편차는 하트비트 송신 시점 차이로 설명된다).

## ★★ 게이트웨이가 이것을 랩어라운드로 오인한다 — 코드로 확인했다

`gateway/fw_adapter.py::_unwrap_nt()` 는 **`delta < -2147.48 s` 이면 랩으로 판정**하고
이후 값에 `4294.967 s` 를 더한다. 관측된 역행 −3057.7 s 는 그 문턱을 넘는다.

실제 시퀀스를 그 함수에 그대로 먹여 본 결과:

| 원시 `nt` | 보정 후 |
|---|---|
| 3078.2 | 3078.200 |
| **20.5** | **4315.467** ← 랩 보정 발동 |
| 24.0 | 4318.967 |

    실제 역행량     3057.7 s
    보정이 더한 값  4294.967 s
    ★ 주입되는 오차 1237.3 s

**즉 이 사건 뒤의 모든 사망 시각이 약 1237초 미래로 밀린다.**
대본 B 에서 인접 사망 간격이 약 328초이므로 **1237초는 네 칸 가까운 오차**다.
합성 실험 §(c) 에서 「시각이 크게 어긋나면 방향이 90.9°까지 무너진다」고 잰 바로 그 조건이다.

**★ 이것은 추정이 아니라 코드를 돌려 확인한 결과다.** 다만 아직 **실제 사망 데이터로는
재현하지 않았다**(이 소크에서는 아무도 죽지 않았다).

## 원인 — **미확정.** 두 가설이 살아 있다

| | 가설 | 이 가설을 지지하는 것 | 반대되는 것 |
|---|---|---|---|
| **H1** | **허브 전원 순간 저하 → 노드 6대 동시 재부팅** | 여섯 대가 **동시에** 재설정됐다. 브리지만 무사한데 **브리지는 노트북에 직결**돼 있고 나머지는 **같은 허브**에 있다. 재부팅하면 `nt` 는 0 부터 다시 센다 | 노드 자기 시리얼을 읽지 않아 `rst:0x` 를 못 봤다 |
| **H2** | 재부팅 없이 painlessMesh 시간축만 재설정 | 노드끼리는 여전히 서로 동기돼 있다 | 여섯 대가 정확히 같은 순간에 그럴 이유를 아직 못 찾았다 |

**가르는 방법은 하나뿐이다 — 노드 자기 시리얼에 `rst:0x` 가 찍히는지 보는 것.**
그래서 55분 시점에 `scripts/node_reset_watch.py` 로 **COM6(n11) 의 자기 시리얼**을
같이 읽기 시작했다(읽기 전용, 175분).

> **기록해 둘 것:** 그 포트를 여는 순간 n11 이 한 번 재부팅됐다(우리가 낸 DTR 리셋).
> **소크 경과 약 3304초 지점의 n11 이탈 1회는 우리가 만든 것이다.** 분석에서 빼야 한다.
> 그리고 그 리셋 중에 **`E BOD: Brownout detector was triggered`** 가 찍혔다 —
> 우리가 낸 리셋 와중이라 단정할 수 없지만, **공급이 빠듯하다는 신호**이므로 H1 쪽에 무게가 실린다.

## ★ 촬영에 주는 함의 — 이게 4시간 소크의 가장 큰 수확이다

- **런 1회가 1320초(22분)** 인데, 이 사건은 **55분 안에 1회** 일어났다.
  런 도중에 일어나면 **그 회차는 통째로 버려야 한다.** 확률이 낮지 않다.
- 더 나쁜 것은 **조용히 틀린다**는 점이다. 게이트웨이는 「랩어라운드 감지」라고
  정상적인 경고를 찍고 넘어가며, 1237초 오차는 **화면 어디에도 표시되지 않는다.**
- **D1 리허설 중단 기준(S1~S7)에 이 항목이 없다.** 추가해야 한다.

## 아침에 할 것 (제안 — 사람이 정한다)

1. **런 전 점검에 한 줄 추가:** 게이트웨이 로그에 「랩어라운드 감지」가 뜨면
   **그 회차를 버린다.** 71.58분보다 훨씬 이른 시점에 뜨면 그것은 랩이 아니다.
2. **원인 격리(권장, 30분·펌웨어 무변경):** 노드를 허브에서 빼서
   **개별 USB 포트나 다른 전원**에 물리고 같은 소크를 돌린다. 사건이 사라지면 H1(전원)이다.
3. **고치는 것은 그 다음이다.** 원인을 모른 채 `fw_adapter` 를 고치면
   진짜 랩어라운드 보정을 망가뜨릴 수 있다. **오늘 밤에는 고치지 않았다.**

# 11. ★ 정정과 검증 — 지시받아 다시 잰 것

## 11-1. ★★ 「이탈 405회」는 **계측 산물이었다** — 앞의 §3·§10 을 정정한다

문턱 10초는 **실제 송신 주기 1.518초의 6.6배**라 넉넉해 보였다. 그런데 **수율이 25%면
10초 공백은 우연히도 자주 생긴다.** 기하분포로 검산했다.

모형: 노드가 1.518초마다 보내고 각 패킷이 확률 `p` 로 도착하면 `P(공백 > k주기) = (1-p)^k`.

| 문턱 | 주기 배수 | **무작위 유실 예측** | **관측** | 관측/예측 | 판정 |
|---|---|---|---|---|---|
| 10 s | 6.6× | **674.7** | 418 | **0.62** | **초과 없음 — 전부 무작위 유실로 설명된다** |
| 20 s | 13.2× | 113.0 | **175** | **1.55** | 무작위를 넘는다 = 진짜 이탈 |
| 30 s | 19.8× | 19.1 | **31** | **1.62** | 무작위를 넘는다 = 진짜 이탈 |

**→ 문턱 10초에서 센 405(최종 418)회는 「망이 불안정해서 노드가 이탈한 것」이 아니라
「패킷이 성기게 도착해서 생긴 공백」이다. 내가 앞에서 그것을 이탈이라 부른 것은 틀렸다.**

노드별 도착률: n09 25.4% · n10 24.3% · n11 24.2% · n14 21.6% · n15 23.0% · n16 24.2%.
(앞의 「수율 15%」는 **설정값 1.000초** 기준이었다. **실제 송신 주기 1.518초** 기준으로는 **약 24%** 다.
두 숫자는 같은 사실의 다른 표현이며, 비교 기준을 밝히지 않은 것이 혼동의 원인이었다.)

### 그래서 진짜 문제는 무엇인가

**이탈이 아니라 「전달률 24%」 그 자체다.** 그리고 20초 이상 공백에서 무작위를 1.55배
초과하는 몫(약 62건)이 진짜 이탈이다. **문턱은 20초 이상으로 잡아야 한다.**

**n14 의 606초 침묵은 이 검산과 무관하게 진짜다** — `P(공백>606s) = 0.784^399 ≈ 0` 이다.

## 11-2. ★ 추정기는 크래시하지 않는다. 그리고 **조용한 오답도 아니었다** (3줄)

1. **크래시 0건.** 시각 오염 7종(오보정 +1237s · 역행 −3057s · 음수 사망시각 · 전역 평행이동 ·
   +50000s 이상치 · NaN · +inf) **전부에서 예외 없이 값이 나왔다.**
2. **그런데 오답도 아니었다 — 잔차 게이트가 오염 노드를 걸러낸다.** `+1237.3s` 오보정에서
   국소적합이 16→14로 줄고 **방향 오차는 1.091°** 에 그쳤다(정상 0.248°). 무너지지 않는다.
3. **진짜 위험은 침묵이다.** `NaN` / `+inf` 를 넣어도 **경고 한 줄 없이** 그 노드만 조용히
   빠지고(15/16) 값이 나온다. 데이터가 망가져도 로그에 흔적이 안 남는다.

### ★ §9 의 내 서술을 정정한다

§9 에서 「1237초 오차 → 합성 실험 §(c) 의 90.9° 조건」이라고 썼는데 **그것은 과장이었다.**
§(c) 의 90.9° 는 **두 노드의 시각을 같은 값으로 붕괴시킨** 경우였고,
지금 문제는 **한 덩어리를 통째로 평행이동**시키는 경우다. **둘은 다른 고장이다.**
실제로 그 오염을 그대로 넣어 재보니 **1.091°** 였다.

**그래도 랩 규칙은 그대로 필요하다.** 이유가 바뀔 뿐이다 —
「방향이 무너져서」가 아니라 **「사망 시각 대장이 오염되고, 그것이 조용히 일어나서」**다.
사망 시각은 이 프로젝트의 **원자료**다. 방향이 우연히 견뎠다고 원자료 오염을 넘길 수는 없다.

# ★★★ 12. 원인 확정 — 노드가 **브라운아웃으로 재부팅**하고 있다

## 12-1. 먼저 — 앞서 쓴 「브라운아웃 흔적 0건」을 정정한다

§4 에서 「브라운아웃·리셋 흔적 0건」이라고 썼다. **그것은 브리지 시리얼만 본 결과였다.**
노드의 재부팅 메시지는 **그 노드 자신의 시리얼**로만 나가고 메시로 전파되지 않는다.
**브리지만 보면 노드 재부팅은 원리적으로 보이지 않는다.** 내 관측 설계의 구멍이었다.

## 12-2. 노드 자기 시리얼에서 직접 본 것 (n11 / COM6, 14.3분)

    t =   0.0 ~ 823.3 s   리셋 **0줄**. 정상 동작.
    t = 823.4 ~ 857.4 s   E BOD 44회 + rst:0x3 (SW_RESET) 45회
                          ★ 0.78초 간격의 **브라운아웃 부팅 루프** (34.0초 지속)
    t = 858.4 s           MESHID 배너 → 부팅 성공, 회복

`E BOD: Brownout detector was triggered` → `rst:0x3 (SW_RESET)` 이 34초 동안
**44번 반복**됐다. 전압이 브라운아웃 문턱 근처에서 오르내렸다는 뜻이다.

## 12-3. ★ 인과를 시각으로 못 박았다

브리지 로그에서 **n11 의 34.7초 이탈이 소크 t=4467.1 에 끝난다.**
노드 쪽 부팅 루프는 **35.0초**(823.4→858.4)였다. **0.3초 이내로 일치한다.**

    확정 오프셋 = 4467.1 − 858.4 = 3608.7 s

즉 **「노드가 브라운아웃으로 재부팅한다」와 「브리지가 이탈로 본다」가 같은 사건**이다.
(앞서 오프셋을 3304 s 로 잡았던 것은 `summary.json` 이 5분마다 갱신돼 305초 낡았기 때문이다.
 이 대조로 정확한 값을 얻었다.)

## 12-4. ★★ 그런데 이탈의 **대부분은 재부팅이 아니다** — 두 현상이 섞여 있다

노드 시리얼에 **리셋이 한 줄도 없던 13.7분** 동안, 브리지는 같은 노드의 이탈을
**11회** 기록했다(지속 10.6 · 12.1 · 12.1 · 13.6 · 14.4 · 14.4 · 15.1 · 15.1 · 15.9 · 16.6 · **30.5** 초).

**→ 이 11회는 재부팅이 아니다. 순수 패킷 유실이다.** §11-1 의 기하분포 검산과 정확히 맞는다.

**주의 — 「25초 넘으면 재부팅」은 성립하지 않는다.** 위 목록에 **30.5초짜리 순수 유실**이 있다.
지속시간만으로는 두 원인을 가를 수 없다. **노드 시리얼을 봐야만 갈린다.**

| 현상 | 정체 | 증거 | 비중 |
|---|---|---|---|
| **A. 만성 패킷 유실** | 노드→루트 전달률 약 24% | 기하분포 검산 · 리셋 없는 구간의 이탈 11회 | **이탈의 대부분** |
| **B. 브라운아웃 부팅 루프** | 전원 부족 | `E BOD` 44회 · 34초 루프 · 시각 0.3초 일치 | 14.3분에 **1회 관측** |

## 12-5. §9 의 시계 재설정도 이것으로 설명된다

t≈2527 에 **노드 6대가 동시에** `nt` 를 ~0 으로 되돌렸다. B(브라운아웃 재부팅)로 보면 자연스럽다:

- 노드 하나만 재부팅하면 **살아남은 이웃의 시간축에 다시 동기**되므로 `nt` 역행이 안 보인다.
  실제로 n11 이 t=4432 에 재부팅했을 때 `NT_WRAP` 이벤트가 **없었다.**
- 그런데 **여섯 대가 한꺼번에** 재부팅하면 옛 시간축을 들고 있는 노드가 하나도 안 남는다.
  → 집단이 **0 부터 다시 시작**한다. 그게 t≈2527 의 6건 동시 역행이다.
- 브리지는 **노트북 USB 에 직결**돼 있어 브라운아웃을 겪지 않았다. 그래서 시계가 끊기지 않았고,
  지금 노드 집단과 **2537초 어긋나** 있다.

**이 설명은 관측 전부와 모순 없이 들어맞는다. 다만 t≈2527 당시에는 노드 시리얼을
보고 있지 않았으므로 「강한 추론」이지 직접 관측은 아니다.** 그렇게 표시해 둔다.

## 12-6. ★ 근본 원인은 전원이다 — 이미 예측돼 있던 것

`docs/전력설계_기록.md` 에 이렇게 적혀 있다:

    노드 1개 순간 피크 ~240 mA (WiFi TX 802.11n)
    16노드 최악 동시 피크 약 3.8 A   ← 3 A 초과 ⚠

**11구 허브가 노드 6~7대를 감당하지 못하고 있다.** 브리지만 무사한 이유도 이것으로 설명된다 —
**브리지는 허브가 아니라 노트북 USB 포트에 직결**돼 있다.

## 12-7. 아침에 할 것 — 우선순위가 바뀐다

**이제 1순위는 「하트비트 유실 격리」가 아니라 「전원」이다.**

1. **전원부터 바꾼다.** 허브를 빼고 **전원 공급이 되는 허브(외부 어댑터)** 또는
   노드를 나눠 물린다. 그리고 **같은 소크를 다시 돌린다.**
   판정: `E BOD` 가 사라지는가 · 전달률 24%가 올라가는가.
2. **노드 시리얼을 반드시 같이 본다.** 브리지만 보면 재부팅이 안 보인다 —
   이번에 그 구멍에 빠졌다. `scripts/node_reset_watch.py` 를 최소 1대에 건다.
3. **런 전 전원 재인가(§0-0)는 그대로 지킨다.** 브라운아웃과 별개로 필요하다.

**★ 이 상태로 촬영하면 안 된다.** 22분 런 도중 노드가 브라운아웃으로 재부팅하면
그 노드의 사망 시각이 오염되고(제약③), 여섯 대가 함께 재부팅하면 §9 의 집단 시계 재설정이
런 한가운데서 일어난다.

# 13. LED 흰색 — 소스 확인 결과 (n04 재굽기 전 검증)

## 13-1. ★ 「부팅 보라 0.4초」는 현재 빌드에서 **원래 안 뜬다**

`firmware/node/node.ino:249~265` 의 `printModeBanner()`:

```c
void printModeBanner() {
#if FAKE_TEMP_RAMP
  ...
  // LED: 합성 모드면 부팅 시 보라 1회 깜빡
  led.setPixelColor(0, led.Color(80, 0, 80)); led.show(); delay(400);
  led.clear(); led.show(); delay(200);
#else
  Serial.println(F("[REAL SENSOR MODE] DS18B20 on GPIO4"));
  ...
#endif
}
```

**보라 점멸은 `#if FAKE_TEMP_RAMP` 안에 있다.** 그런데 굽기는 `flash_node.ps1` 이
**`-DFAKE_TEMP_RAMP=0`** 으로 한다(전 17대 동일).

**→ 보라는 하드웨어가 완전히 정상이어도 안 뜬다. 이것을 하드웨어 판정 기준으로 쓰면
   정상 보드를 불량으로 판정하게 된다.**

## 13-2. `led.begin()` 순서는 정상이다

`setup()` 은 `Serial.begin` → **`led.begin()`** → `delay(300)` → `printModeBanner()` →
`setLed()` 순서다. `begin()` 이 먼저다. 문제 없다.

## 13-3. NODE_ID 로 LED 가 갈리는 코드는 **없다**

`NODE_ID` 는 HB/LG/DV/ST 패킷 필드와 부팅 배너에만 쓰인다.
LED 경로(`setLed()` — `ALIVE` 초록 `(0,90,0)` / `DYING`·`DEAD` 빨강 `(120,0,0)`)에는
**어떤 분기도 없다. 모든 노드가 동일하게 동작한다.**

## 13-4. ★★ 그래서 흰색의 의미가 달라진다 — 전원과 연결된다

`setLed()` 는 **`setup()` 끝에서야** 실행된다. 그 전에 죽으면 WS2812 는 데이터를 한 번도
못 받고 **흰색(미초기화)** 으로 남는다.

**그리고 우리는 방금 노드가 브라운아웃 부팅 루프에 빠지는 것을 직접 봤다**(§12).
루프에 빠진 노드는 `setup()` 을 완주하지 못한다.

**→ 「흰색 LED 8대」가 납땜 불량이 아니라 전원 문제의 증상일 수 있다.**
이 가설은 §12 와 독립적으로 세워진 것이 아니라, §12 관측이 만든 것이다.

### 유효한 육안 판정은 하나뿐이다

| 관찰 | 뜻 |
|---|---|
| **부팅 직후 초록** | `setup()` 완주 + LED 배선 정상 |
| **흰색** | `setLed()` 가 실행되지 못했다 — **배선 불량 또는 setup 미완주(브라운아웃)** |
| 보라 | **현재 빌드에서는 나오지 않는다.** 판정에 쓰지 말 것 |

### 가르는 법 (아침 5분)

n04 를 **노트북 USB 에 직결**한다(허브 말고 — 전원 변수를 없앤다).

- 초록이 뜨면 → **보드 정상.** 허브에서 흰색이었던 것은 전원 문제였다.
- 여전히 흰색이고 배너·HB 는 정상이면 → **LED 배선 불량.** 재납땜.
- 배너가 안 나오거나 `E BOD` 가 보이면 → 그 보드 자체의 전원 문제.

## 14-1. 관측값 (31.1분)

| 메시 합류 | **O** | O |

## 14-3. 판정 — **보드는 죽지 않았다. 다만 「LED 재납땜만 필요」로 확정하기엔 이르다**

- **보드 정상 쪽 근거:** 메시에 합류하고 하트비트를 낸다. 굽기 기록도 PASS(`index 3`).
  **「보드 불량」 가설은 이것으로 기각된다.**

  **재부팅하면 `setLed()` 가 실행되기 전 상태로 돌아가므로 LED 가 흰색으로 보이는 것과 모순되지 않는다.**
  즉 **흰색의 원인이 배선인지 전원인지 아직 갈리지 않았다.**

### 가르는 법 — 전원 변수를 없애고 본다

**n04 한 대만 노트북 USB 에 직결**한다(허브 금지). 그 상태에서:

| 관찰 | 결론 |
|---|---|
| **초록** | 배선 정상. 허브에서 흰색이던 것은 **전원 문제**였다 |
| **흰색인데 배너·HB 정상** | **LED 배선 불량.** 재납땜 |
| 배너가 안 나오거나 `E BOD` | 그 보드 자체의 전원 문제 |

**「부팅 보라 0.4초」는 판정에 쓰지 말 것** — 현재 빌드(`-DFAKE_TEMP_RAMP=0`)에서는
하드웨어가 정상이어도 안 뜬다(§13-1).

## 14-4. 재굽기는 하지 않았다

지시는 「다시 굽고 배너 확인」이었으나, **굽기 전 소스 확인(§13)에서 답의 절반이 나왔고**
(보라는 원래 안 뜬다 · NODE_ID 분기 없음), **소크에서 n04 가 합류·하트비트를 내는 것이
확인되어 「굽기가 꼬였다」 가설도 약해졌다.** 배너는 굽기 당시 이미 `index 3` 로 통과했다.

**남은 것은 전원 변수를 없앤 육안 확인 하나뿐이라, 그것을 먼저 하는 편이 싸다.**
그래도 재굽기를 원하면 n04 를 노트북에 직결해 두면 바로 굽는다.

# 16. ★★ n04 LED 판정 완료 — **배선 불량. 보드는 정상**

## 16-1. 대조 시험 — 전원 변수를 없앴다

n04 **한 대만 노트북 USB 에 직결**(허브 금지)한 상태에서 관측.

| 확인 항목 | 결과 |
|---|---|
| 부팅 원인 | `rst:0x1 (POWERON_RESET)` — **정상 전원 인가** |
| **`E BOD`** | **0건** — 노트북 직결에서는 브라운아웃이 없다 |
| 모드 배너 | `[REAL SENSOR MODE] DS18B20 on GPIO4` · `{"fake":0}` |
| MESHID 배너 | `id 3 · mid 3179103081 · is_root 0 · role NODE · thr 80.0 · warn 60.0` — **전부 정상** |
| 부팅 소요 | 배너까지 **1.12초** |
| **LED 색 (육안)** | **흰색** |

## 16-2. 판정

**`setLed()` 는 실행됐는데 LED 가 흰색이다. → WS2812 가 데이터를 못 받고 있다.**

세 가지가 차례로 배제됐다:

1. **펌웨어 아님** — 같은 빌드가 n01·n02 에서 초록으로 확인됐고, `setLed()` 에 `NODE_ID` 분기가 없다(§13-3).
2. **굽기 사고 아님** — 배너가 `index 3` 로 정확하고 `thr`/`warn` 도 맞다. 굽기 기록도 PASS.
3. **전원 아님** — 노트북 직결에서 `E BOD` 0건, `POWERON_RESET` 으로 깨끗하게 부팅한다.

**→ 남는 것은 WS2812 로 가는 경로다: 데이터선(GPIO5) 납땜 · LED 모듈 · 그라운드.**

## 16-3. ★ 결론

    보드 정상 — LED 재납땜만 필요.

지시받은 판정 기준(「합류·하트비트가 정상이면 보드 정상, LED 재납땜만 필요」)을 충족한다:
n04 는 소크에서 **메시 합류 + 하트비트 186건**을 냈고(§14), 노트북 직결에서 **깨끗하게 부팅**한다.

## 16-4. 다른 흰색 보드에 대한 함의 — **일반화하지 말 것**

n04 의 원인이 배선이라고 해서 **나머지 흰색 보드도 배선이라는 뜻은 아니다.**
§12 에서 본 것처럼 브라운아웃 부팅 루프에 빠진 노드도 `setup()` 을 완주 못 해 흰색으로 남는다.
**각 보드마다 같은 대조 시험(노트북 직결 → 초록인가)을 해야 갈린다.**

| 관찰 (노트북 직결) | 원인 |
|---|---|
| 초록 | 허브에서 흰색이던 것은 **전원** 문제 |
| **흰색 + 배너 정상** | **LED 배선** — n04 가 여기 해당 |
| 배너 없음 / `E BOD` | 그 보드 자체 전원·부팅 문제 |

## 16-5. 재납땜 시 확인할 것

    ① GPIO5 (PIN_NEOPIXEL) → WS2812 DIN 데이터선 도통
    ② WS2812 5V · GND 도통
    ③ LED 모듈 자체 불량 가능성 — 다른 보드의 LED 와 바꿔 끼워 보면 1분에 갈린다

**★ 「부팅 보라 0.4초」로 확인하지 말 것.** 현재 빌드(`-DFAKE_TEMP_RAMP=0`)에서는
하드웨어가 완전히 정상이어도 보라가 뜨지 않는다(§13-1). **초록으로 판정한다.**
