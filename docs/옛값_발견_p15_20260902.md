## 1. 무엇이 틀렸나

덱 **p15**(인쇄번호 15 · '자기 차단'은 정보 부족이었나, 우리 상수였나)에 이런 값이 있다.

| 위치 | 현재 (옛값) | 맞는 값 | 근거 |
|---|---|---|---|
| 타일 각주 | 이웃 통과 **182 s** | **346 s** | `spacing/v = 0.2 / 0.0005785` |
| 타일 각주 | 반경 **327 s** | **622 s** | `radio_range/v = 0.36 / 0.0005785` |
| 하단 본문 | 20cm 벤치의 화선은 **1.1 mm/s** | **0.58 mm/s** | `deploy_config.json` `v_front_expected = 0.0005785` |

세 값 모두 **v = 0.0011 m/s 시절의 산술**이다. `0.2/0.0011 = 181.8` · `0.36/0.0011 = 327.3` —
자기들끼리는 맞아떨어지므로 검사에 안 걸렸다. **기준이 되는 v 가 바뀐 것이 문제였다.**

출처는 `docs/D1_드라이런_20260830.md:39` — 8/30 드라이런 때 `0.36 / 0.0011 = 327.3 s` 로 찍혀 있다.

## 3. 그러면 「왜 622 s 는 안 재봤나」가 남는가 — 아니다. 이미 재봤다

타일을 622 s 로 고치면 스윕 최대(327 s)를 넘어선다. 심사에서 나올 수 있는 질문이다.
**답은 본편 산출물 안에 있다.**

`results/hw/run_205330_raw.log`
```
dt_window     = radio_range_m / v = 0.36 / 0.0005785 = 622.3 s
alert_horizon = spacing_m     / v = 0.2  / 0.0005785 = 345.7 s
```

**본편 런(9/1)은 dt_window = 622.3 s 로 돌아 16/16 · 방향오차 2.85° 를 냈다.**
즉 스윕(8/30, ≤327 s)은 **문제를 진단한 기록**이고, 유도값 622.3 s 는 **본편에서 검증됐다.**
둘은 다른 시점의 다른 역할이지 모순이 아니다.

> 발표에서 물으면: 「스윕은 8월 30일 진단 기록이고, 최종 유도값 622.3초는 9월 1일 본편 런에서
> 16/16으로 검증했습니다. 시작 로그에 유도식이 그대로 찍혀 있습니다.」

`gateway/gateway.py:86-89` **주석**:

```

```
