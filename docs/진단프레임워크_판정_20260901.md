받은 프레임워크를 그대로 실행하지 않았다. 아래는 **무엇을 왜 취하고 버렸는지**와 그 결과물이다.

## 0. 이 문서에 대한 비판 — 가장 큰 맹점

**이 문서는 주 위험을 「진단 능력 부족」으로 본다. 그러나 현재 주 위험은 「시간」이다.**

마감 9/3, 하드웨어는 **오늘 밤 한 번**. 문서를 그대로 실행하면:

- 도구 6개 제작 · 펌웨어 계측 추가 · 17대 재굽기에 남은 시간을 쓴다
- 결정적 런 **직전에 변수를 늘린다** → **문서 자신의 원칙 A(한 번에 하나만) 위반**

그래서 「진단 구조를 세운다」는 목표는 받되, **오늘 밤 블로커를 푸는 데 실제로 쓰이는 것만** 만들었다.

또 하나: §5 의 「값이 튄다(25.1 → 81.7 → 25.4)」 예시는 **우리가 관측한 적 없는 증상**이다.
없는 증상을 쫓으면 시간만 없어진다. 외부에서 온 증상 목록을 우리 증상으로 착각하지 않는다.

### D-1. §11 이 찾아낸 것 — painlessMesh 에 **루트를 알린 적이 없다**

`firmware/node/node.ino` 에 등록된 콜백은 **`onReceive` 하나뿐**이고,
`setRoot()` · `setContainsRoot()` 는 **호출하지 않는다.** 문서·펌웨어 전체 언급 0건.
즉 브리지는 **우리 코드에서만** 루트(`NODE_IS_ROOT`)이고 라이브러리는 루트의 존재를 모른다.

painlessMesh 공식 문서:

> **"At most one node in the mesh should be a root, or you could end up with multiple subMeshes."**
> "It is recommended that any AP_ONLY nodes (e.g. a bridgeNode) be set as a root node."
> "If one node is root, then it is also recommended to call `setContainsRoot()` on all the nodes."
> `setRoot()` — "can speed up mesh formation" / `setContainsRoot()` — "restructure more quickly around the root"

**우리 증상(서브메시 분할, 합류 40~62초)과 정확히 맞는다.** 다만:

- 라이브러리 경고: 루트가 없는데 `setContainsRoot()` 만 켜면 **역효과**. 둘은 같이 가야 한다
- 적용하려면 **17대 재굽기**가 필요하고, 오늘 아침 **재인가 후 16/16 합류가 됐다**
- 그래서 **즉시 적용하지 않는다.** 실험 큐 H5 로 올린다 (문서 §18 금지사항 준수)

## B. DATA PATH FAILURE MAP

증거가 있는 것만 적는다. 없는 칸은 **NOT OBSERVED** 로 남긴다(원칙 E).

| 경계 | 상태 | 관측 방법 | 현재 증거 | 의심 failure mode |
|---|---|---|---|---|
| **T0** 노드 | ✅ 정상(간접) | 판 위 LED · 사망시험 | 아침 점호 16/16 응답, 온도 25.5~26.5℃ 정상, 센서의심 0 | — |
| **T1** 브리지 mesh RX | ⚠ **NOT OBSERVED** | `TOPO n_peers` 만 있음 | 아침엔 16노드 전부 브리지를 거쳐 보고됨 | 계측 없음(수신 카운터·drop 카운터 부재) |
| **T2** 브리지 serial TX | ⚠ **NOT OBSERVED** | 브리지 자기 출력 | 부팅 배너·`MESHID`·`ROOT_READY` 는 **정상 출력됨** | 출력 큐/backpressure 계측 없음 |
| **T3** 파이 RAW | ❌ **깨짐 (확정)** | `cat` · `check_serial_integrity.py` | `,"max_alloc":110580,"peers":0}` 가 초당 수백 회. **펌웨어는 5초에 1회만 찍는다** → ESP32 발신 불가능 | **stale_replay** — USB-UART/드라이버/포트 |
| **T4** 파서 | ✅ 무죄(증명됨) | `cat`(파이썬 없이) | 파이썬 없이도 동일 → **파서 원인 아님** | — |
| **T5** gateway/dashboard | ⚠ 미검사 | — | T3 가 깨진 동안 판단 불가 | — |

**첫 번째로 깨지는 계층 = T3.** 그러므로 **T4·T5(파서·게이트웨이)를 고치는 것은 금지**된다.
T2↔T3 경계(브리지 USB-UART 칩 ↔ 파이 포트/드라이버)를 좁히는 것이 다음 할 일이다.

## C. MESH / TIME MAP

### 물리 topology vs mesh topology

| | 현재 상태 |
|---|---|
| 물리 이웃 | `deploy_config.json` 실측 좌표로 결정. 추정기 전용 |
| mesh topology | painlessMesh 가 결정. **관측 수단이 `TOPO n_peers`(정수) 뿐** |
| 분리 여부 | ✅ **개념적으로 이미 분리돼 있고 문서화됨** |
| **문제** | `TOPO_FULL_SUBTREE 0` 으로 **부모/자식 관계 출력을 껐다**(8/31 힙 절약). 즉 **누가 누구에게 붙었는지 볼 수 없다** → 「군집」을 실제로 검증할 수단이 없다 |

> 되살리려면 `-DTOPO_FULL_SUBTREE=1` (브리지만 재굽기). 힙을 다시 먹으므로 **런에는 켜지 않는다.**
> 진단 전용으로만 쓴다 — 이건 문서 §10 의 「A(실제 군집) vs B(관측 착시)」를 가르는 유일한 방법이다.

### 시계 3종

| 시계 | 필드 | 성질 | 현재 처리 |
|---|---|---|---|
| node local | `ms`, `t` | 노드마다 다름. **비교 불가** | ✅ 어댑터가 폴백으로만 쓰고 `time_source="local_millis"` 로 표시 |
| mesh 공유 | `nt` | 비교 가능. **정본** | ✅ 우선 채택, 랩어라운드(71.58분) 보정 구현됨 |
| host | — | 파이/노트북 수신 시각 | ⚠ **기록 안 함** — 비용 0으로 추가 가능한데 안 되어 있다 |

**미계측 (UNRESOLVED)**: `onNodeTimeAdjusted` 콜백 **미등록**. 즉 mesh 시각이 **언제 얼마나 조정됐는지
기록이 없다.** 오늘 밤 관측된 "uptime 62분/49분 시각오염"이 (a) 랩어라운드인지 (b) 재합류 후
시각 재동기인지 **현재 증거로는 구분 불가**.
