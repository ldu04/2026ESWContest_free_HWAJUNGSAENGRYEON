# 라즈베리파이 게이트웨이 준비 절차 (2026-08-31)

헤드리스 파이를 **SSH 접속 → 코드 전송 → 한 줄 실행 → 기동 확인**까지 가져가는 문서.
촬영은 **내일(9/1)** 이다. 파이가 안 되면 §6 의 노트북 폴백으로 즉시 갈아탄다.

관련 문서: 당일 실행표는 `docs/D1_리허설_절차서.md`, 보드 굽기는 `docs/굽기_절차서_20260831.md`.

## 0. 전제 — SD카드 굽기는 이 문서 밖이다

    무엇이 위험한가 : 디스크를 한 글자 잘못 고르면 시스템 드라이브가 통째로 지워진다
                      (저장소·덱·촬영본이 전부 사라진다)
    되돌릴 수 있나  : 없음
    그래서 어떻게   : Raspberry Pi Imager(GUI)로 **사람이 직접**. 스크립트로 자동화하지 않는다

`docs/강령_위험작업.md` §1 에 따라 이 문서의 어떤 명령도 디스크에 쓰지 않는다.

### 굽기 전에 Imager 의 「고급 설정」에서 확인할 것

헤드리스라 이걸 빠뜨리면 **부팅 후 아무 방법으로도 접속할 수 없다.**

| 항목 | 값 |
|---|---|
| 호스트명 | `bulsa`  → 접속은 `bulsa.local` |
| SSH 사용 | **켬** (비밀번호 또는 공개키) |
| 사용자 이름·비밀번호 | 직접 지정 — Bookworm 부터 기본 `pi/raspberry` 가 **없다** |
| Wi-Fi SSID / 비밀번호 | 촬영 장소에서 실제로 잡히는 망 |
| Wi-Fi 국가 | `KR` — 이걸 안 넣으면 무선이 아예 안 올라온다 |
| OS 종류 | **64비트** — §3 의 numpy 때문에. 아래 박스 참조 |

> ### ★ 반드시 64비트 이미지
> `gateway/requirements.txt` 는 `numpy==2.4.4` 로 고정돼 있고, 이 버전은
> **aarch64(64비트) 휠만** 배포된다. 32비트(armhf) 이미지에 깔면 pip 이 소스 컴파일로
> 넘어가 파이에서 수십 분을 끌다 대개 실패한다. `setup_pi.sh` 가 §1 에서 이걸 먼저 경고하지만,
> 그때는 이미 다시 구워야 하는 상황이다. **굽기 전에 고른다.**

> 고급 설정을 빠뜨린 채 이미 구웠다면 — 확실한 해결은 **Imager 로 다시 굽는 것**이다.
> (부팅 파티션에 `ssh` 빈 파일 / `userconf.txt` 를 넣는 우회가 알려져 있지만
> Bookworm 은 `custom.toml` + `firstrun.sh` 로 바뀌어 Imager 버전에 따라 동작이 갈린다.
> 촬영 전날 밤에 검증되지 않은 우회로 시간을 쓰지 않는다.)

## 1. SSH 첫 접속

파이에 전원을 넣고 **1~2분** 기다린다(첫 부팅은 파일시스템 확장 때문에 느리다).

### 1-1. 먼저 이것부터

```powershell
ping -4 bulsa.local
ssh <사용자>@bulsa.local
```

`-4` 를 붙이는 이유: IPv6 로 먼저 붙으려다 실패해 「안 되는 것처럼」 보이는 경우가 있다.

### 1-2. `.local` 이 안 될 때 — 위에서부터 순서대로

`.local` 은 mDNS 다. Windows 11 은 내장 지원이 있지만 공유기·보안소프트웨어가 막으면 안 뜬다.
**IP 를 직접 찾으면 그만이다.**

| # | 방법 | 명령 / 위치 |
|---|---|---|
| 1 | 이름을 IP 로 풀어본다 | `Resolve-DnsName bulsa.local -Type A` |
| 2 | **공유기 관리페이지**의 DHCP 접속 목록 | 보통 `192.168.0.1` 또는 `192.168.1.1`. 이름에 `bulsa` 또는 제조사 `Raspberry Pi` 로 보인다 |
| 3 | ARP 표 | `arp -a` — 파이 랜카드 MAC 은 `b8:27:eb` · `dc:a6:32` · `d8:3a:dd` · `e4:5f:01` 로 시작한다 |
| 4 | 서브넷 훑기 | `nmap -sn 192.168.0.0/24` (nmap 이 있을 때) |
| 5 | **유선 랜으로 직결** | 무선 설정이 틀렸을 때 가장 확실하다. 공유기에 랜선으로 꽂고 2번을 다시 본다 |
| 6 | HDMI + 키보드 한 번 | 화면에서 `hostname -I` 로 IP 를 직접 읽는다. 무선 설정이 틀렸는지도 여기서 바로 보인다 |

IP 를 찾았으면 그걸로 붙는다:

```powershell
ssh <사용자>@192.168.0.42
```

> **호스트키 경고**가 뜨면(전에 같은 이름/IP 로 다른 파이에 붙은 적이 있는 경우):
> `ssh-keygen -R bulsa.local` 로 그 항목만 지우고 다시 붙는다. SD카드를 다시 구우면
> 파이의 호스트키가 새로 생기므로 **정상적인 경고**다.

## 2. 저장소를 파이로 옮기기

### ★ 방법 결정: **scp 로 tar 한 덩이를 보낸다**

| 후보 | 채택 여부 | 이유 |
|---|---|---|
| `git clone` | **불가** | 이 저장소는 **원격이 하나도 없다**(`git remote -v` 가 빈 출력). 공개 전이라 만들 수도 없다 |
| USB 메모리 | 안 씀 | 헤드리스 파이에 물리적으로 꽂아야 하고, Pi OS Lite 는 자동 마운트를 안 해서 `lsblk` → `mount` 를 손으로 해야 한다. 단계가 늘고 얻는 게 없다 |
| `git bundle` | 안 씀 | 파이에서 풀려면 **git 이 먼저 필요한데**, git 을 깔아주는 게 `setup_pi.sh` 다(닭-달걀). tar 는 어떤 리눅스에도 이미 있다 |
| **scp + tar** | **채택** | 어차피 SSH 로 들어간다 — 추가 의존성이 0이다. Windows 11 에는 `scp`·`tar` 가 기본 탑재다. 전송량 **약 260 KB**, 몇 초면 끝난다 |

### ★ `git archive` 가 아니라 **작업트리**를 묶는 이유

`git archive HEAD` 는 **커밋된 것만** 담는다. 그런데 촬영 직전에 반드시 바뀌는 파일이
`gateway/deploy_config.json` 이다 — `scripts/apply_measured_coords.py` 가 실측 좌표를 여기에 쓴다.
그게 아직 커밋 전이면 `git archive` 는 **옛 명목 좌표를 조용히 실어 보낸다.**
방향 추정이 통째로 틀어지는데 화면에는 그럴듯한 각도 하나만 나온다. 그래서 작업트리를 묶는다.

### 2-1. 노트북에서 — 묶어서 보낸다 (PowerShell)

```powershell
cd <저장소 루트>

# 게이트웨이 실행에 필요한 것만. docs/ 의 pptx·mp4(6 MB)와 results/(30 MB)는 뺀다.
tar.exe -czf "$env:USERPROFILE\failsafe-mesh-pi.tar.gz" `
        --exclude=__pycache__ --exclude=.venv `
        sim gateway scripts dashboard

scp "$env:USERPROFILE\failsafe-mesh-pi.tar.gz" <사용자>@bulsa.local:~/
```

무엇이 왜 들어가는지:

| 디렉터리 | 왜 필요한가 |
|---|---|
| `gateway/` | 게이트웨이 본체 + `deploy_config.json`(좌표 정본) |
| `sim/` | **필수.** 게이트웨이는 `sim/estimator.py`·`network.py`·`verification.py` 를 그대로 재사용한다 |
| `scripts/` | `setup_pi.sh`, `apply_measured_coords.py`(좌표 실측 반영) |
| `dashboard/` | 파이가 대시보드를 서빙하고 노트북 브라우저로 볼 때 필요(§5) |

### 2-2. 파이에서 — 푼다

```bash
mkdir -p ~/failsafe-mesh && tar -xzf ~/failsafe-mesh-pi.tar.gz -C ~/failsafe-mesh
ls ~/failsafe-mesh          # gateway  sim  scripts  dashboard 네 개가 보여야 한다
```

### 2-3. 나중에 파일 하나만 고쳤을 때

다시 다 보낼 필요 없다. 그 파일만 덮어쓴다:

```powershell
scp gateway\deploy_config.json <사용자>@bulsa.local:~/failsafe-mesh/gateway/
```

## 3. `setup_pi.sh` 실행 — 한 줄

```bash
bash ~/failsafe-mesh/scripts/setup_pi.sh
```

이 한 줄이 하는 일 (전부 **멱등** — 두 번 돌려도 안전하다):

| § | 하는 일 | 왜 |
|---|---|---|
| 1 | 아키텍처·OS·python3 확인 | aarch64 가 아니면 numpy 를 못 깐다고 **미리** 말한다 |
| 2 | `python3-venv` `python3-pip` `git` 설치 | 이미 있으면 `apt update` 조차 건너뛴다 |
| 3 | `~/failsafe-mesh/.venv` 생성 | **PEP 668** — 아래 박스 |
| 4 | `gateway/requirements.txt` 설치 후 **import 해서** 검증 | 깔린 것과 불러와지는 것은 다른 문제다 |
| 5 | `dialout` 그룹 추가 | 없으면 `/dev/ttyUSB0` 에서 Permission denied |
| 6 | **ModemManager 끄기** | 아래 박스 |
| 7 | `/dev/ttyUSB*` · `lsusb` 로 브리지 인식 확인 | |
| 8 | **스모크 테스트** — 합성 스트림으로 파이프라인 전체 통과 | 보드 없이 파이 쪽 변수를 오늘 밤에 다 없앤다 |

> ### PEP 668 — venv 를 쓴다 (`--break-system-packages` 아님)
> Bookworm 은 시스템 파이썬을 externally-managed 로 잠가 전역 pip 설치를 막는다.
> `--break-system-packages` 로 뚫으면 apt 가 관리하는 numpy(1.24 대) 위에
> pip 의 numpy 2.4.4 가 덮여 `dist-packages` 안에서 **버전이 뒤섞인다.**
> 그 고장은 조용하고, 되돌리려면 사실상 OS 를 다시 굽는 수밖에 없다.
> venv 는 되돌리기가 `rm -rf ~/failsafe-mesh/.venv` 한 줄이고 시스템은 안 건드린다.
> 이 프로젝트는 numpy 를 버전 고정해 쓰므로(수치 재현성) 어느 numpy 가 로드됐는지
> 모르는 상태를 만들면 안 된다. **대가는 실행할 때 `.venv/bin/python` 을 쓰는 것뿐이다.**

> ### ModemManager 를 왜 끄나
> ModemManager 는 새로 뜬 `/dev/ttyUSB*` 를 모뎀으로 의심하고 **AT 명령을 밀어 넣는다.**
> ESP32 브리지에 그게 들어가면 JSON 라인 사이에 쓰레기가 섞이거나 포트를 몇 초 붙잡는다.
> 증상이 「가끔 프레임이 빈다」뿐이라 촬영 중에는 절대 못 잡는다.
> 되돌리기: `sudo systemctl enable --now ModemManager`

### 3-1. ★ dialout 그룹은 재접속해야 적용된다

`setup_pi.sh` 가 「로그아웃 후 다시 접속」이라고 찍으면 **반드시 그렇게 한다.**
지금 열려 있는 SSH 세션에는 그룹 변경이 적용되지 않는다.

```bash
exit
ssh <사용자>@bulsa.local
id -nG | tr ' ' '\n' | grep -x dialout      # dialout 이 찍히면 적용된 것이다
```

## 4. 게이트웨이 기동 확인 — 무엇이 찍히면 정상인가

### 4-1. 보드 없이 (setup_pi.sh §8 이 자동으로 돌린다)

`setup_pi.sh` 끝에 이게 나오면 파이 쪽은 끝난 것이다:

```
[OK]   파이프라인 정상 — 재구성 프레임 42개
```

프레임 **0개**면 실패다. 이 프로젝트의 대표적 침묵실패라서 스크립트가 숫자로 못 박아 검사한다.

### 4-2. 실보드 — 시작 로그 통과 기준

```bash
cd ~/failsafe-mesh
.venv/bin/python gateway/gateway.py --fw --port auto --emit-dashboard \
    --out-deaths results/hw/d1_deaths.csv
```

> **`--fw` 는 필수다.** 빼면 펌웨어 방언(`MODE/ROOT_READY/ST/HB/LG/DV/DC`)을 못 읽어
> `META` 가 안 잡히고 **프레임 0개**로 조용히 끝난다. (`gateway/README.md` 「두 방언」)
>
> **`--port auto`** 는 COM/tty 번호를 고정하지 않고 포트를 돌며 `role=ROOT(bridge)` 를 찾는다.
> 다른 USB 구멍에 꽂아도 살아남는다. 못 찾으면 **시끄럽게 죽는다**(종료코드 2) — 빈 입력으로
> 조용히 도는 것보다 낫다.

찍혀야 하는 것 **세 덩이**:

#### ① 규모 상수 유도 — 값을 고르지 않고 물리에서 유도한다

```
[gateway] 규모 상수 유도 (v_front_expected = 0.0005785 m/s):
           dt_window     = radio_range_m / v = 0.36 / 0.0005785 = 622.3 s
           alert_horizon = spacing_m     / v = 0.2 / 0.0005785 = 345.7 s
           speed_true    = v_front_expected  = 0.0005785 m/s  (별도 상수 삭제)
           residual_gate_s = 165.1 s  (2026-09-01 실물 런에서 재도출, 표본 8건)
```

> ★ [2026-09-01] D-075(텀 압축)로 v 가 0.523 → **0.5785 mm/s** 가 됐다(총 런 25:48 → 23:19).
> 이 블록이 **옛 값(0.000523 · 688.3 · 382.4 · 69.1)으로 남아 있어 `tools/check_truth.py` 가 잡았다.**
> D1 절차서는 고쳤는데 같은 블록이 여기 하나 더 있는 것을 놓쳤다 — 사본이 둘이면 이런 일이 난다.

| 봐야 할 것 | 정상 | 이상하면 |
|---|---|---|
| `dt_window` | **622.3 s** | 시뮬 기본값 **8 s** 가 찍히면 `v_front_expected` 가 안 읽힌 것이다. 벤치 규모에서 8 s 는 국소 적합 **16/16 전멸**이 확인된 값이다 — 그 회차는 방향이 안 나온다 |
| `residual_gate_s` | **165.1 s** | 「미설정 → sim 기본값」이 찍히면 `deploy_config.json` 이 옛 파일이다. 분기③이 전건 기각될 수 있다 |
| 네 줄이 아예 없음 | — | `deploy_config.json` 에 `v_front_expected` 가 없다. 전송이 옛 버전이다 (§2-3 으로 다시 보낸다) |

#### ② 좌표 경고 — **촬영 회차에는 안 떠야 한다**

```
[gateway] ***** 좌표 경고: 좌표 미실측 — 명목 격자값 사용 중. 추정 결과를 실측으로 보고하지 말 것. *****
[gateway] 좌표 출처 = 명목(미실측)
```

지금 저장소의 `deploy_config.json` 은 `measured: false` 라 **이 경고가 뜬다.**
런 전에 실측 좌표를 반영해야 사라진다 (`D1_리허설_절차서` 0-5 / 0-6):

```bash
.venv/bin/python scripts/apply_measured_coords.py coords.txt --dry-run   # 검산만
.venv/bin/python scripts/apply_measured_coords.py coords.txt             # 반영
```

| 찍히는 것 | 뜻 |
|---|---|
| `좌표 출처 = 실측`, 경고 없음 | **통과.** 이 회차는 실측으로 보고할 수 있다 |
| `좌표 출처 = 명목(미실측)` | 런은 되지만 **결과를 실측으로 보고할 수 없다.** 사망 대장 각 행에 그대로 박히고 나중에 지울 수 없다 |
| `좌표 출처 = 실측(의심)` | `measured=true` 인데 좌표 16개가 명목 격자값과 **전부 일치**한다. 실측값을 옮겨 적지 않았거나 플래그만 켠 것이다 |
| `좌표 출처 = 미상` | `deployment.measured` 키가 없다. 옛 설정 파일이다 |

#### ③ 배치검산 3줄 — 좌표를 잘못 적어도 게이트웨이는 조용히 돈다

```
[gateway] 배치검산 ① 최근접거리 중앙값 0.200 m (노드 16개)
[gateway] 배치검산 ② 이웃수 분포 {3: 4, 5: 8, 8: 4}  (4x4 정격자 기대값 {3: 4, 5: 8, 8: 4})
[gateway] 배치검산 ③ 라벨 규약  nXX -> id = XX-1  (n01->id0 … n16->id15)
```

| 줄 | 통과 기준 | 어긋나면 |
|---|---|---|
| ① | `spacing_m`(0.2 m) 과 **2% 이내**. 벗어나면 뒤에 `★ 설정 spacing_m=... 과 어긋난다` 가 붙는다 | 좌표표의 단위(cm↔m)나 자릿수를 의심한다 |
| ① 노드 수 | **16개** | 16이 아니면 좌표표에 빠진 노드가 있다 |
| ② | 정확히 `{3: 4, 5: 8, 8: 4}` | 어긋나면 좌표가 한 칸 밀렸거나 `radio_range_m` 이 다르다 |
| ③ | 항상 같은 문구 | 대본은 `n01`, 코드는 `id 0`. **한 칸 밀리면 방향이 통째로 뒤집힌다** |

> ②가 맞고 ①이 어긋나는 경우가 제일 위험하다 — 격자 모양은 맞는데 **축척만 틀린** 것이라
> 화면에는 그럴듯한 각도가 나온다. ①을 눈으로 확인한다.

#### 그리고 브리지를 찾았다는 줄

```
[bridge] /dev/ttyUSB0 에서 브리지를 찾았다: id=99 role=ROOT(bridge) mid=...
```

`id=99` 여야 한다(`config.h` 의 `BRIDGE_INDEX`). 못 찾으면 다음이 찍히고 **종료코드 2** 로 죽는다:

```
!! 브리지를 찾지 못했다. role=ROOT(bridge) 인 포트가 없다.
```

### 4-3. 런을 끝내는 법 — Ctrl-C

`--port auto` 로 실보드에 붙으면 입력 스트림이 끝나지 않는다. **Ctrl-C 가 정상적인 종료 수단이다.**

Ctrl-C 를 누르면 게이트웨이가 **읽은 데까지로** 요약·사망 대장 CSV·대시보드 데이터를 쓰고
**종료코드 0** 으로 끝난다. 먼저 이 줄이 찍힌다:

```
[gateway] ***** 중단(Ctrl-C) — 읽은 데까지로 산출물을 쓴다 *****
```

**중단됐다는 사실은 산출물 두 곳에 남는다** — `fake`·`coord_source` 와 같은 원칙이다:

| 어디에 | 무엇이 |
|---|---|
| **요약 헤더** | `[요약] … · 중단=1` 과 바로 아래 `***** 중단된 회차 — 이 산출물은 런의 앞부분뿐이다 … *****` |
| **사망 대장 CSV** | `interrupted` 열. **행마다** 박힌다 — 헤더에만 두면 CSV 를 잘라 붙이는 순간 사라진다 |

> **`중단=1` 인 회차는 런의 앞부분뿐이다.** 사망 건수를 '전부'로 읽으면 안 된다.
> 대본은 16건인데 12번째에서 끊었다면 CSV 에는 12행만 있고, 나중에 보면 "12건만 죽었다"로 읽힌다.
> `D1_리허설_절차서` 3-2(사망 시각 16개 대조) 전에 **이 열부터** 본다.

> META 를 한 번도 못 받고 끊기면(너무 이르게 끊었거나 `--fw` 누락) 대시보드 데이터만 건너뛰고
> `⚠ META 를 한 번도 못 받아 …` 를 찍는다. 요약과 CSV 는 그대로 나오고 죽지 않는다.

### 4-3-1. 원문 로그가 따로 필요할 때

`D1_리허설_절차서` 3-1 은 브리지 **원문** 로그(`results/hw/mesh_*.log`)를 요구한다.
게이트웨이 산출물과 별개의 제출물이다. 원문을 먼저 받고, 끝난 뒤 그 파일을 다시 먹인다.

> ★ 이 방법과 §4-3 의 실시간 실행은 **동시에 못 한다** — 시리얼 포트는 한 프로세스만 연다.
> 둘 중 하나를 고른다. 원문 로그가 필요하면 이쪽, 화면으로 진행을 보려면 §4-3 쪽이다.

```bash
cd ~/failsafe-mesh
mkdir -p results/hw

# ① 브리지가 어느 포트인지 한 번만 확인한다 (로그의 [bridge] 줄을 보고 Ctrl-C)
.venv/bin/python gateway/gateway.py --fw --port auto | head -20

# ② 런 시간(1320 s)보다 넉넉히 잡아 원문을 받는다. 시간이 차면 **스스로 끝난다**
.venv/bin/python - /dev/ttyUSB0 1400 results/hw/d1_raw.log <<'PY'
import sys, time, serial
port, secs, out = sys.argv[1], float(sys.argv[2]), sys.argv[3]
ser = serial.Serial(port, 115200, timeout=1)
t0, n = time.time(), 0
with open(out, "w", encoding="utf-8") as f:
    while time.time() - t0 < secs:
        raw = ser.readline()
        if not raw:
            continue
        line = raw.decode("utf-8", "ignore").strip()
        if line:
            f.write(line + "\n"); f.flush(); n += 1
            print(line, flush=True)
print("[capture] %d 줄 → %s" % (n, out))
PY

# ③ 받은 원문을 게이트웨이에 먹인다 — 여기서 요약·CSV·대시보드가 전부 나온다
.venv/bin/python gateway/gateway.py --in results/hw/d1_raw.log --fw --emit-dashboard \
    --out-deaths results/hw/d1_deaths.csv
```

②의 원문 로그는 `D1_리허설_절차서` 3-1 이 요구하는 `results/hw/mesh_*.log` 그 자체라
**어차피 남겨야 하는 파일**이다.

> 이 경로는 2026-08-31 에 검증했다(476줄 원문 → 재구성 프레임 42개 → CSV·대시보드 정상 산출).

## 6. ★ 폴백 — 노트북으로 게이트웨이를 돌린다

> **이 절은 처음 보는 사람이 그대로 따라 하도록 썼다.** 파이 지식은 필요 없다.
> 2026-08-31 밤에 시뮬레이션 입력으로 §6-2 ~ §6-6 을 **끝까지 돌려 확인했다.**
> 확인하지 못한 것은 §6-8 에 따로 적었다 — 그것만 아침에 사람이 봐야 한다.

### 6-0. 언제 갈아타나 — 시각을 미리 정해둔다

| 신호 | 판단 |
|---|---|
| §1 SSH 접속이 **15분** 안에 안 됨 | 폴백 |
| §3 `setup_pi.sh` 가 numpy 에서 실패 | 폴백 |
| §4-2 에서 브리지를 못 찾음(`exit 2`) | 파이에서 한 번 재시도 → 그래도 실패면 폴백 |

**촬영 시작 예정시각 60분 전을 마지노선으로 잡는다.** 그 시각이 되면 파이를 포기하고
폴백으로 간다. 파이를 계속 붙잡다가 촬영을 못 하는 것이 최악이다.

### 6-1. 전제 — 노트북에 준비할 것은 없다

저장소가 이미 있고 `python 3.14.3` · `numpy 2.4.4` · `pyserial 3.5` 가 깔려 있다
(2026-08-31 확인). **전송도 venv 도 필요 없다.** 파이와 다른 것은 두 가지뿐이다.

| | 파이 | 노트북 |
|---|---|---|
| 시리얼 포트 이름 | `/dev/ttyUSB0` | `COM3` 등 — 그래서 **양쪽 다** `--port auto` 를 쓴다 |
| 파이썬 | `.venv/bin/python` | `python` |

### 6-2. 브리지를 꽂는다 — 이것부터

브리지 보드 **하나만** 노트북 USB 에 직결한다(허브 금지). 노드는 판 전원으로 따로 켠다.

    # 브리지가 보이는지 먼저 확인한다 (PowerShell)
    [System.IO.Ports.SerialPort]::GetPortNames()

`COM16` · `COM17` 은 **블루투스 가상 포트라 보드가 아니다**(이 노트북 고정). 그 둘 말고
새 `COMx` 가 하나 보여야 한다. 안 보이면 케이블을 바꾼다 — 충전 전용 케이블이 섞여 있다.

### 6-3. 돌린다 — 명령 한 줄

```powershell
cd <저장소 루트>
python gateway\gateway.py --fw --port auto --emit-dashboard `
       --out-js dashboard\data.js `
       --out-deaths results\hw\d1_deaths.csv
```

**★ `--out-js dashboard\data.js` 를 빠뜨리지 마라.** 기본값은
`results\dashboard\gateway_data.js` 인데 **대시보드 화면은 그 파일을 읽지 않는다.**
`dashboard\index.html` 은 같은 폴더의 `data.js` 만 읽는다. 이 플래그가 없으면
브라우저에 **2026-07-28 시뮬레이션(10 m 격자)** 이 그대로 뜬다 — 촬영본에 그게 찍히면
남의 데이터를 우리 실측인 것처럼 보여준 셈이 된다.

`dashboard\data.js` 는 git 이 추적하는 파일이라 덮어써도 되돌릴 수 있다:

    git checkout -- dashboard/data.js

### 6-4. 시작 로그 — 무엇이 보이면 정상인가

§4-2 의 통과 기준이 **노트북에서도 똑같다.** 네 덩이가 순서대로 나와야 한다.

1. **규모 상수 4줄** — `dt_window` / `alert_horizon` / `speed_true` / `residual_gate_s`.
   값을 고른 게 아니라 `v_front_expected` 하나에서 유도된 것이다.
2. **좌표 경고** — 촬영 회차에는 **안 떠야 한다**. 뜨면 실측 좌표를 아직 안 넣은 것이다(§6-7).
3. **배치검산 3줄** — 최근접거리 중앙값 `0.200 m` / 이웃수 분포 `{3: 4, 5: 8, 8: 4}` /
   라벨 규약 `nXX -> id = XX-1`. **분포가 기대값과 다르면 좌표를 잘못 적은 것이다.**
4. **브리지를 찾았다는 줄** — 여기까지 오면 시리얼은 붙은 것이다.

### 6-5. 끝내는 법 — Ctrl-C 가 정상 종료다

`--port auto` 는 스트림이 끝나지 않는다. **Ctrl-C 가 유일한 종료 수단이고, 그게 맞다.**
Ctrl-C 를 받으면 읽은 데까지로 산출물을 전부 쓴다. 강제로 창을 닫지 마라 — 산출물이 안 나온다.

### 6-6. 산출물 3개 — 이게 다 나오면 성공이다

| # | 무엇 | 어디 | 확인법 |
|---|---|---|---|
| 1 | **요약** | 화면(stdout) | `[요약] 사망 N건 → 채택 …` 줄이 있다 |
| 2 | **사망 대장 CSV** | `results\hw\d1_deaths.csv` | 행마다 `fake` 열이 있다. 실물이면 **`fake=0`** |
| 3 | **대시보드** | `dashboard\index.html` 을 브라우저로 연다 | 서버 불필요. 판이 화면을 채운다 |

#### ★ 마지막 두 줄을 보고 놀라지 마라 — 정상이다

    [gateway] estimator 재사용 결과(최종): 방향오차=None°, 속도오차=None%, 사망=16, 경보=0

- **`방향오차=None`** — 실물에는 참값(ground truth)이 없다. 그래서 오차를 계산하지 않는다.
  **정상이다.** 방향 자체는 대시보드와 스냅샷에 들어 있다.
- **`경보=0`** — 이것은 **마지막 프레임 하나**의 경보 수다. 그때는 이미 전부 죽어 있어서 0 이다.
  전 구간 경보는 대시보드 타임라인에서 본다. (시뮬 확인값: 최초 경보 **t = 331 s**,
  최대 동시 경보 **7건**, 1323 프레임 중 **990 프레임**에서 경보 표시.)

**즉 이 두 줄로 성패를 판단하지 마라.** 판단은 위 표의 산출물 3개로 한다.

### 6-7. 실패했을 때 — 종료코드로 가른다

| 종료코드 | 뜻 | 할 일 |
|---|---|---|
| `2` | 브리지를 못 찾았다 (`role=ROOT(bridge)` 인 포트 없음) | 브리지가 꽂혔나 · `NODE_ID 99` 로 구워졌나(`docs/보드대장_MAC_NODEID.md`) |
| `3` | numpy / pyserial 이 없다 | `python -m pip install numpy pyserial` |

**블루투스 포트는 자동탐색을 막지 않는다.** 보드가 하나도 없는 상태로 실측한 결과,
`COM16` 은 열기에 실패하고 `COM17` 은 응답이 없는데도 **11.4초 만에 크게 실패**하고
멈춰 서지 않았다. 조용히 빈 입력으로 도는 일은 없다.

### 6-8. ★ 아직 확인하지 않은 것 — 아침에 사람이 볼 것

- ~~실물 브리지로 `--port auto` 를 태워본 적이 없다~~ → **2026-08-31 해소.**
  **파이에서 직접 확인했다**(브리지가 `/dev/ttyUSB0` 에 꽂힌 상태):

      [bridge] /dev/ttyUSB0 에서 브리지를 찾았다: id=99 role=ROOT(bridge) mid=4113565437
      [gateway] 규모 상수 유도 (v_front_expected = 0.000523 m/s): … 4줄   ← [2026-08-31] 당시 값(옛 v)
      [gateway] 좌표 출처 = 실측                    ← 좌표 경고가 뜨지 않는다
      [gateway] 배치검산 ① 최근접거리 중앙값 0.199 m (노드 16개)
      [gateway] 배치검산 ② 이웃수 분포 {3: 4, 5: 8, 8: 4}  (기대값과 일치)
      [gateway] 배치검산 ③ 라벨 규약  nXX -> id = XX-1

  **§6-4 의 네 덩이가 전부 나온다.** 파이에서 돌리는 경로는 이제 검증됐다.
- **시리얼 포트를 열면 DTR/RTS 로 브리지가 재부팅된다.** 무해하지만, 게이트웨이를 켜는
  순간 브리지가 한 번 리셋된다는 것을 알고 있어라. 메시는 몇 초 안에 다시 붙는다.
- **좌표는 아직 명목값(미실측)이다.** 촬영 회차 전에 §6-4 의 2번 경고가 사라져야 한다.
  넣는 법은 `scripts/apply_measured_coords.py`.

### 6-9. 덱과의 불일치는 기술 문제가 아니다

덱에는 「게이트웨이: 라즈베리파이」라고 적혀 있다. 노트북으로 촬영하면 덱을 고치든가
촬영을 다시 하든가인데, **그 판단은 사용자가 한다.** 이 문서는 「기술적으로 된다」까지만 말한다.

## 7. 안 될 때 — 증상별

| 증상 | 원인 | 조치 |
|---|---|---|
| `bash: ...setup_pi.sh: /usr/bin/env: bad interpreter` 또는 `'\r': command not found` | 스크립트가 CRLF 로 전송됐다 | `sed -i 's/\r$//' ~/failsafe-mesh/scripts/setup_pi.sh` (저장소에 `.gitattributes` 로 `*.sh text eol=lf` 를 넣어 앞을 막아뒀다) |
| `error: externally-managed-environment` | venv 밖에서 pip 을 썼다 | `.venv/bin/python -m pip` 을 쓴다. §3 박스 참조 |
| numpy 설치가 몇 분째 컴파일 중 | 32비트 이미지다 | 중단(Ctrl-C). 64비트로 다시 굽거나 §6 폴백 |
| `Permission denied: '/dev/ttyUSB0'` | dialout 그룹 미적용 | §3-1 — **로그아웃 후 재접속** |
| `/dev/ttyUSB*` 가 없다 | 케이블·전원·드라이버 | 충전 전용 케이블이 아닌지 확인 → `lsusb` 에 `10c4:ea60` 가 뜨는지 → `dmesg \| tail -30` |
| `!! 브리지를 찾지 못했다` (종료코드 2) | 브리지가 `NODE_ID 99` 로 안 구워졌다 | `docs/굽기_절차서_20260831.md`. `is_root=1` 인 보드가 **정확히 한 대**여야 한다 |
| 프레임 0개인데 오류는 없다 | `--fw` 를 빠뜨렸다 | `--fw` 를 붙인다. §4-2 박스 |
| `dt_window = 8.0 s` 로 찍힌다 | 옛 `deploy_config.json` | §2-3 으로 다시 보낸다 |
| `중단=1` 인데 사망이 16건이 안 된다 | 런 도중에 끊었다 — **정상 동작**이다 | 그 회차는 앞부분뿐이다. 전부로 보고하지 않는다(§4-3) |
| Ctrl-C 했는데 대시보드만 안 나왔다 | META 전에 끊겼거나 `--fw` 누락 | 로그에 `⚠ META 를 한 번도 못 받아…` 가 있는지 확인 → `--fw` 확인 |
| 프레임이 가끔 빈다 | ModemManager 가 포트에 개입 | `systemctl is-active ModemManager` 확인 → `sudo systemctl disable --now ModemManager` |
| SSH 호스트키 경고 | SD카드를 다시 구웠다(정상) | `ssh-keygen -R bulsa.local` |
