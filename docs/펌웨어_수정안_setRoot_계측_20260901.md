# 펌웨어 수정안 — `setRoot` + 계측 콜백 (2026-09-01, **미적용 · 제안**)

> **아직 적용하지 않았다.** 21:00 에 하드웨어가 다 모였을 때 결정한다.
> 적용하려면 **17대 재굽기**(오늘 밤 실적 기준 30~45분, 실패 0건).

---

## 왜 — 우리는 painlessMesh 에 루트를 **알린 적이 없다**

`firmware/node/node.ino` 의 현재 상태:

- 등록된 콜백: **`onReceive` 하나뿐**
- `setRoot()` · `setContainsRoot()`: **호출 없음** (저장소 전체 언급 0건)
- 브리지는 **우리 코드의 `NODE_IS_ROOT`** 로만 루트다 — 라이브러리는 모른다

painlessMesh 공식 문서:

> **"At most one node in the mesh should be a root, or you could end up with multiple subMeshes."**
> "It is recommended that any AP_ONLY nodes (e.g. a bridgeNode) be set as a root node."
> "If one node is root, then it is also recommended to call `setContainsRoot()` on all the nodes in the mesh."
> `setRoot()` — "can speed up mesh formation"
> `setContainsRoot()` — "will cause the mesh to restructure more quickly around the root node.
> However, this could have **adverse effects if set, while there is no root node present**."

**우리 증상과 일치**: 서브메시 분할(n01·n02·n03·n06·n07 이 한 덩어리로 무응답),
합류 시간 40~62초, 개별·브리지 리셋으로 복구 안 됨.

⚠ **확실한 해법이라고 말하지 않는다.** 「우리가 라이브러리 권고를 어기고 있었다」는 사실은
확정이지만, 「그것이 우리 분할의 원인이었다」는 **미검증**이다(원칙 E).
다만 *지금 상태가 문서상 비권장 구성이라는 것*은 논쟁의 여지가 없다.

---

## 수정 1 — 루트 지정 (동작 변경)

`node.ino` `setup()`, `mesh.onReceive(&onReceive);` **바로 다음**:

```c
  mesh.init(MESH_PREFIX, MESH_PASSWORD, &userScheduler, MESH_PORT);
  mesh.onReceive(&onReceive);

  // ★★ [2026-09-01] painlessMesh 에 루트를 알린다.
  //   지금까지 브리지는 **우리 코드에서만** 루트였고 라이브러리는 몰랐다.
  //   문서: 루트가 지정되지 않으면 **subMesh 가 여러 개 생길 수 있다.**
  //   ⚠ 둘은 반드시 같이 간다 — 루트가 없는데 setContainsRoot 만 켜면 역효과라고 문서가 경고한다.
#if NODE_IS_ROOT
  mesh.setRoot(true);                 // 브리지 1대에서만
#endif
  mesh.setContainsRoot(true);         // 루트 포함 **전 노드**에서
```

## 수정 2 — 계측 콜백 (동작 불변, **브리지에서만 출력**)

```c
  // ── 계측 전용. 동작을 바꾸지 않는다. **이벤트가 날 때만** 짧은 줄을 찍는다 ──
  //   ★ 왜 짧고 이벤트 기반이어야 하나: TOPO 의 subConnectionJson() 이 5초마다 577자
  //     String 을 만들다가 힙을 말려 브리지를 크래시시킨 전례가 있다
  //     (docs/브리지_크래시_20260831.md). 아래는 String 을 만들지 않는다.
  //   ★ 왜 브리지에서만: 노드의 Serial 은 아무도 안 읽는다(USB 는 브리지만 꽂힌다).
  //     메시로 실어 보내면 그게 바로 (가′)로 줄인 트래픽을 도로 늘리는 짓이다.
#if NODE_IS_ROOT
  mesh.onNodeTimeAdjusted([](int32_t offset) {
    Serial.print(F("{\"type\":\"TADJ\",\"off\":")); Serial.print(offset);
    Serial.print(F(",\"ms\":"));                    Serial.print(millis());
    Serial.println(F("}"));
  });
  mesh.onChangedConnections([]() {
    Serial.print(F("{\"type\":\"CONN\",\"n\":"));   Serial.print(mesh.getNodeList().size());
    Serial.print(F(",\"ms\":"));                    Serial.print(millis());
    Serial.println(F("}"));
  });
#endif
```

**이 두 줄이 메우는 구멍** (`docs/진단프레임워크_판정_20260901.md` 참조):

    Topology observability : NOT READY → 부분 READY  (CONN 으로 피어 증감을 시각과 함께 본다)
    Clock observability    : PARTIAL   → READY       (TADJ 로 mesh 시각 조정을 수치로 본다)

`TADJ` 가 없으면 「uptime 이 꼬였다」가 **랩어라운드인지 재동기인지 영영 구분 못 한다.**
게이트웨이는 모르는 타입을 조용히 버리므로(`dropped_types`) **추가해도 기존 파이프라인은 안 깨진다.**

## 검증 계획 — **2대만으로 먼저 확인한다** (판 없이)

재굽기 전에 브리지 + 여분 ESP32 **2대로** 위험을 없앤다:

| 단계 | 하는 일 | 확인할 것 |
|---|---|---|
| 1 | 여분 ESP32 를 **일반 노드**(예 NODE_ID 0)로, 브리지를 **루트**로 굽는다 | 컴파일 통과 · 배너 정상 |
| 2 | 둘만 켜고 시리얼 관측 | `CONN` 이 찍히는가 · 합류까지 몇 초인가 |
| 3 | 노드 전원만 뺐다 켠다 | 재합류 시간 · `TADJ` 발생 여부/크기 |

**2대에서 위 셋이 다 정상이면** 17대 재굽기의 위험은 사실상 컴파일·동작 확인이 끝난 상태가 된다.
2대에서 이상하면 **17대를 굽지 않는다.**
