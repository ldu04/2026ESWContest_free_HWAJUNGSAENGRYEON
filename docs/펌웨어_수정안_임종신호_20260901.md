# 수정 ① — `HEARTBEAT_MS` 를 낮춘다 (병목을 비운다)

## `firmware/node/config.h`

```diff
-#define HEARTBEAT_MS       1000     // heartbeat_period 1.0s
-#define SILENCE_TIMEOUT_MS 3000     // silence_timeout 3.0s
+// ★ [2026-09-01] 1000 -> 5000.
+//   근거: 브리지가 내보내는 노드 메시지가 **초당 1.3개**인데(2h 소크 실측),
+//   노드 15대가 1 Hz 로 보내면 15개/초라 6배 초과공급이다. 그 결과 도착률이 7.3%로
+//   내려앉고, **단발인 임종신호가 91% 유실된다**(n07 실사망 시험 실패).
+//   5000 이면 3개/초 → 도착률 약 43%(계산). 반복(수정 ②)과 곱해 유실 5.8%가 된다.
+#define HEARTBEAT_MS       5000     // heartbeat_period 5.0s
+// ★ 반드시 함께 바꾼다. 이 값은 **하트비트 3회분**이라는 뜻이다.
+//   3000 그대로 두면 하트비트 0.6회분이 되어 **살아 있는 노드를 죽었다고 투표한다.**
+#define SILENCE_TIMEOUT_MS 15000    // silence_timeout 15.0s (= 3 x HEARTBEAT_MS)
```

### 대가 — 정직하게 적는다

| | 이전 | 이후 |
|---|---|---|
| 침묵 기반 사망 감지 지연 | 3초 | **15초** |
| 온도 갱신 주기(화면·음성) | 1초 | **5초** |

- 침묵 감지는 **예비 경로**다. 주 경로(임종신호)가 살아나므로 순손실은 아니다.
- 대본의 사망 간격은 최소 20초(`n14`)이므로 **15초 지연이 사망 순서를 뒤집지 않는다.**
- `scripts/soak_watch.py` 의 `HB_PERIOD_S = 1.0` · `DROP_S = 10.0` 도 같이 올려야
  이탈 집계가 맞는다(감시 도구라 굽기와 무관, 나중에 고쳐도 된다).

# 수정 ② — 임종신호를 여러 번 보낸다 (**첫 각인을 들고**)

## 왜 「첫 각인」이 핵심인가

`sendJson()` 은 **호출할 때마다** `nt` 를 다시 찍는다:

    node.ino:114   doc["nt"] = nodeTimeSec();   // 매 호출마다 새로 각인

그래서 `sendLastGasp()` 를 그냥 5번 부르면 사본마다 시각이 다르고,
**게이트웨이에 3번째 사본이 먼저 도착하면 사망 시각이 그만큼 늦게 기록된다.**
제약③(사망 시각 = 당사자 노드의 각인)이 형식적으로는 지켜지지만 **값이 오염된다.**

→ **각인은 한 번, 전송은 여러 번.** 완성된 문자열을 만들어 두고 그걸 재전송한다.

## `firmware/node/config.h` — 상수 추가

```diff
 #define LAST_GASP_DELAY_MS 300      // last_gasp_delay 0.3s
+// ★ [2026-09-01] 임종신호 반복. 단발이면 도착률 그대로가 도달 확률이다.
+//   간격을 1초로 벌린 이유: 병목이 「가득 찬 큐」이면 짧은 간격의 반복은 **같이 버려진다.**
+//   벌려야 상관이 줄어든다. 사망 시각은 첫 각인을 그대로 들고 가므로 늦어지지 않는다.
+#define LAST_GASP_REPEATS  5        // 총 전송 횟수(첫 1회 포함)
+#define LAST_GASP_GAP_MS   1000     // 반복 간격
```

## `firmware/node/node.ino` — 상태 변수 (`lastGaspSent` 근처, 약 57행)

```diff

+// ★ 임종신호 재송 상태. payload 를 **문자열로 굳혀** 두는 것이 요점이다 —
```

## `firmware/node/node.ino` — `loop()` 안, 하트비트 블록 **앞** (약 439행)

```diff
+  // ★ 임종신호 재송 — **DEAD 이후에도 계속한다.** 여기가 이 수정의 전부다.
+  //   DEAD 는 하트비트를 멈추게 하지만(도배 방지), 임종신호는 반대로 **끝까지 보내야** 한다.
+  //   같은 문자열을 그대로 다시 쏘므로 사망 시각은 첫 각인 그대로다.
+  //   게이트웨이·중계 양쪽이 첫 LG 만 채택하므로 중복 사망은 생기지 않는다
+  //   (fw_adapter.py:359 · node.ino:240 에서 확인).
+  if (lgSendsLeft > 0 && (int32_t)(millis() - lgNextMs) >= 0) {
+    mesh.sendBroadcast(lgPayload);
+    if (NODE_IS_ROOT) { Serial.println(lgPayload); }
+    lgSendsLeft--;
+    lgNextMs = millis() + LAST_GASP_GAP_MS;
+  }
+
   // 1) 하트비트(ALIVE만)
   if (state == ALIVE && now - lastHb >= HEARTBEAT_MS) {
     lastHb = now; broadcastHeartbeat();
   }
```

> `(int32_t)(millis() - lgNextMs) >= 0` 로 쓴 이유: `uint32_t` 뺄셈의 언더플로를 피한다.
> 이 프로젝트는 같은 자리에서 이미 한 번 당했다 — `dyingAtMs` 언더플로로
> **임종신호가 나가기 전에 DEAD 가 발동**했다(node.ino:428~434 주석).

| # | 확인 | 어떻게 |
|---|---|---|
| 1 | 컴파일 | `firmware/tools/burn_one.ps1` 이 부르는 빌드가 통과하는가 |

| 6 | 침묵 오탐이 없는가 | `SILENCE_TIMEOUT_MS` 를 같이 안 올리면 여기서 터진다 |

# 이 안을 쓰지 않기로 할 경우

- **(라) 브리지 loop() 가 왜 0.5초인지부터 본다**가 근본 해결이다.
  그게 고쳐지면 처리량 1.3개/초 자체가 올라가고 이 수정이 필요 없을 수도 있다.
- 다만 **원인이 미확정**이라 시간이 얼마나 들지 모른다. 마감은 9/3 이다.
- 최소한 **수정 ②(반복)만이라도** 넣으면 유실 91.3% → 63.6% 로 준다.
  목표(7%)에는 못 미치지만 **아무것도 안 하는 것보다 낫다.**
